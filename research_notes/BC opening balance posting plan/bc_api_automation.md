# Business Central Online: programmatic creation and posting of opening-balance journals (API v2.0, custom AL, S2S OAuth)

Research method note: `learn.microsoft.com` and most community blogs were unreachable from this environment (egress proxy denied them), so Microsoft documentation was read from its public source repository (`MicrosoftDocs/dynamics365smb-devitpro-pb`, `main` branch) and the API behaviour was verified directly against Microsoft's shipped AL source for the API v2.0 app and Base Application (`microsoft/BCApps`, `main`, i.e. the current BC 27/28-era code). Each finding cites the Learn URL and/or the GitHub source file. Community claims that could only be read via search snippets are marked as such.

## Key Question 1: Standard API v2.0 — `journals`, `journalLines`, bound action `Microsoft.NAV.post` (URLs, schemas, writable fields, account types, template constraints)

### Takeaway
The standard v2.0 `journals`/`journalLines` API can create and post lines for **G/L Account, Customer, Vendor and Bank Account** (the page's account-type filter is the enum *range* G/L Account..Bank Account, which includes Customer=1 and Vendor=2), and `POST .../journals({id})/Microsoft.NAV.post` runs codeunit 231 "Gen. Jnl.-Post" and returns 204. However the page **hard-codes `Document Type = " "` (blank)** on every line, exposes no Due Date / Currency Code / Applies-to / Posting Group fields, and resolves `accountId` only for G/L and Bank accounts, so customer/vendor lines must be addressed by `accountNumber` and will post as blank-document-type ledger entries whose due date equals the document (= posting) date.

### Inferences
- Minimal working payloads (derived from the schema and AL above; not copied from a doc):
  - G/L line: `POST .../companies({companyId})/journals({journalId})/journalLines` body `{"accountType":"G/L Account","accountNumber":"1200","postingDate":"2025-12-31","documentNumber":"OPEN-GL-001","amount":1500.00,"description":"Opening balance","balanceAccountType":"G/L Account","balancingAccountNumber":"9999"}` (omit `journalId`; it is implied by the URL).
  - Customer line: `{"accountType":"Customer","accountNumber":"C10000","postingDate":"2025-12-31","documentNumber":"OPEN-INV-1001","externalDocumentNumber":"LEGACY-1001","amount":1200.00,"description":"Opening balance C10000","balanceAccountType":"G/L Account","balancingAccountNumber":"9999"}` — use `accountNumber`, not `accountId`, because the page only resolves `accountId` for G/L/Bank accounts.
  - Vendor line: same with `"accountType":"Vendor"` and a negative `amount` (credit).
- What you **cannot** do with standard `journalLines`: set Document Type (Invoice/Credit Memo), Due Date, Document Date, Currency Code, Applies-to Doc. Type/No., Posting Group, Salesperson, Payment Terms, or Dimension Set ID directly (dimensions go through the `dimensionSetLines` child, see KQ7). Customer/vendor opening entries posted this way become open `Cust./Vendor Ledger Entry` records with blank Document Type and `Due Date = Posting Date`, and the amount is interpreted in the customer's/vendor's default currency (because `Currency Code` is copied from the master record). For aging/dunning fidelity (document type Invoice, original due dates, FCY amounts) a custom AL endpoint is required (KQ3/KQ4).
- The `balanceAccountType`/`balancingAccountNumber` on each line, or `balancingAccountId` on the batch, lets each customer/vendor line be self-balancing against the receivables/payables control account (the classic opening-entry pattern) so no separate balancing G/L line is needed.
- "GENERAL template" constraint: the journal must belong to a template with `Type = General`, non-recurring, `Page ID = General Journal` **only** when relying on the defaults (`POST journals` without `templateDisplayName`, or `GET journals` without a template filter). The line page itself derives template+batch from the batch SystemId, so a batch on any general-journal-type template works once you have its id.
- Because `OnOpenPage` filters `Document Type = " "` and the Account Type range, lines of type Fixed Asset/IC Partner/Employee/Allocation Account created elsewhere are invisible to `GET journalLines`; Customer/Vendor lines are visible (by range). Expect `GET journals({id})/journalLines` to return **zero** lines after a successful post.
- The `post` action's `WebServiceActionResultCode::Deleted` explains the 204/no-content response.

### Gaps
- No Microsoft documentation explicitly states that `journalLines` POST accepts `accountType = Customer/Vendor`; this is inferred from the AL (`Validate("Account Type", Temp."Account Type")` with no restriction) plus the enum range filter. Should be confirmed in the QA sandbox with one customer line.
- Behaviour of supplying `accountId` for a Customer line (whether it is silently ignored or rejected) was not verified.
- Whether `taxCode` on a customer/vendor line is harmful (it writes VAT Prod. Posting Group / Tax Group Code) was not tested; recommend omitting it for customer/vendor lines.

## Key Question 2: `customerPayments` / `customerPaymentJournals` and `vendorPayments` — usable for opening invoices?

### Takeaway
No. These pages hard-code `Document Type = Payment`, `Account Type = Customer/Vendor` and `Applies-to Doc. Type = Invoice`, live on the Cash Receipt / Payment journal templates, and `appliesToInvoiceId` must reference a **posted Sales Invoice Header**; they are for applying payments to existing invoices, not for creating opening receivables/payables.

### Cited Findings
- `customerPayment` properties: `id`, `journalId`, `journalDisplayName` (RO), `lineNumber`, `customerId`, `customerNumber`, `postingDate`, `documentNumber`, `externalDocumentNumber`, `amount`, `appliesToInvoiceId`, `appliesToInvoiceNumber`, `description`, `comment`, `lastModifiedDateTime` (RO); navigation `customerPaymentJournal`, `customer`, `dimensionSetLines` — [customerPayment resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_customerpayment)
- `customerPaymentJournal` properties: `id`, `code`, `displayName`, `lastModifiedDateTime`, `balancingAccountId`, `balancingAccountNumber`; navigation `customerPayments` — [customerPaymentJournal resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_customerpaymentjournal)
- Create example: `POST .../companies({id})/customerPaymentJournals({id})/customerPayments` body with `customerNumber`, `postingDate`, `documentNumber`, `amount`, `appliesToInvoiceNumber`… → 201 — [Create customerPayments](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/api/dynamics_customerpayment_create) (the doc's example URL is abbreviated to `companies({id})/customerPayment`)
- AL page 30055 "APIV2 - Customer Payments" `OnNewRecord`: `Rec."Document Type" := Payment; Rec."Account Type" := Customer; Rec."Applies-to Doc. Type" := Invoice`; `appliesToInvoiceId` must resolve via `SalesInvoiceAggregator.GetSalesInvoiceHeaderFromId` else error `The "appliesToInvoiceId" should be the ID of an Open, Paid, Corrective, or Canceled Invoice.`; `appliesToInvoiceNumber` is looked up in `Sales Invoice Header` — [APIV2CustomerPayments.Page.al](https://github.com/microsoft/BCApps/blob/main/src/Apps/W1/APIV2/app/src/pages/APIV2CustomerPayments.Page.al)
- `SetPaymentsValues` forces `Validate("Document Type", Payment)` and `Validate("Applies-to Doc. Type", Invoice)` — [GraphMgtJournalLines.Codeunit.al](https://github.com/microsoft/BCApps/blob/main/src/Layers/W1/BaseApp/Integration/Graph/GraphMgtJournalLines.Codeunit.al)
- Templates: customer payments use the first non-recurring template with `Page ID = Cash Receipt Journal, Type = 3`; vendor payments `Page ID = Payment Journal, Type = 4` — [GraphMgtJournal.Codeunit.al](https://github.com/microsoft/BCApps/blob/main/src/Layers/W1/BaseApp/Integration/Graph/GraphMgtJournal.Codeunit.al)
- `vendorPayment` has the same shape (`vendorId`, `vendorNumber`, `appliesToInvoiceId/Number`) plus navigation `applyVendorEntries`; `applyVendorEntry` (v18.0+) exposes `applied` (boolean, PATCHable), `appliesToId`, `documentType`, `documentNumber`, `remainingAmount` for multi-entry application — [vendorPayment resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_vendorpayment); [applyVendorEntry resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_applyvendorentry)
- The `journalLine` navigation list includes `customerPaymentJournal`, confirming both pages sit on the same `Gen. Journal Line` table — [journalLine resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_journalline)

### Inferences
- A payment line with no `appliesTo*` posts an **unapplied negative customer entry** (credit) — which could represent an opening customer *credit* balance, but with Document Type = Payment (wrong for aging) and on the cash-receipt template; this is not a sane path for opening invoices.
- After migration, `customerPayments`/`vendorPayments` (+ `applyVendorEntries`) remain the right standard endpoints for applying subsequent payments to opening entries, **but** `appliesToInvoiceId`/`Number` only resolve posted Sales/Purchase Invoice Headers, so opening entries created via journal (no posted invoice document) cannot be targeted via `appliesToInvoice*` — a custom endpoint exposing `Applies-to Doc. Type/No.` or `Applies-to ID` is needed for that too.

### Gaps
- Not verified whether `appliesToInvoiceNumber` resolves a Cust. Ledger Entry document number that has no `Sales Invoice Header` (the AL suggests it does not; `AppliesToInvoiceIdText` is blanked when `SalesInvoiceHeader.Get` fails, but `Applies-to Doc. No.` is still written).

## Key Question 3: Can standard `journalLines` set Document Type, Due Date, Currency, Applies-to, Posting Group? Recommended workaround

### Takeaway
No — none of those are exposed, and Document Type is forced blank. The recommended workaround is a small per-tenant AL extension: a custom API page over `Gen. Journal Line` (exposing Document Type, Document Date, Due Date, Currency Code, Applies-to, Posting Group, Dimension shortcuts) with a `[ServiceEnabled]` bound `post` action, or a codeunit unbound action that takes a JSON document and calls `Gen. Jnl.-Post Batch` in one transaction.

### Cited Findings
- `Gen. Journal Line` table has all required fields: `12 "Currency Code"`, `23 "Posting Group"`, `24 "Shortcut Dimension 1 Code"`, `26 "Salespers./Purch. Code"`, `35 "Applies-to Doc. Type"`, `36 "Applies-to Doc. No."`, `38 "Due Date"`, `47 "Payment Terms Code"`, `48 "Applies-to ID"`, `52 "Reason Code"`, `63 "Bal. Account Type"`, `480 "Dimension Set ID"`, `8001 "Account Id"`, `8006 "Journal Batch Id"` — [GenJournalLine.Table.al](https://github.com/microsoft/BCApps/blob/main/src/Layers/W1/BaseApp/Finance/GeneralLedger/Journal/GenJournalLine.Table.al)
- API pages: `PageType = API`, `APIPublisher`, `APIGroup`, `APIVersion` (pattern `vX.Y` or `beta`), `EntityName`, `EntitySetName`, `ODataKeyFields = SystemId`, `DelayedInsert = true`; naming camelCase alphanumeric; "This page type can't be extended by creating a page extension object"; endpoint `../contoso/app1/v2.0/companies({id})/customers`; `InsertAllowed/ModifyAllowed/DeleteAllowed` restrict operations; `Rec.ReadIsolation := IsolationLevel::ReadCommitted` in `OnOpenPage` exposes only committed data — [API page type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-api-pagetype)
- Custom API walkthrough: use Enums not Options ("Make sure to use Enums instead of Options"), use SystemId as single GUID key (Power Automate/Power Apps need it), expose table-relation fields, child `part` with `SubPageLink` on SystemId yields navigation property and deep insert; `ODataEDMType` is deprecated — [Developing a custom API](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-develop-custom-api)

Jnl.-Post Batch"` directly (what codeunit 231 calls) to avoid the confirm/message/job-queue branches — [APIV2Journals.Page.al](https://github.com/microsoft/BCApps/blob/main/src/Apps/W1/APIV2/app/src/pages/APIV2Journals.Page.al); [GenJnlPost.Codeunit.al](https://github.com/microsoft/BCApps/blob/main/src/Layers/W1/BaseApp/Finance/GeneralLedger/Posting/GenJnlPost.Codeunit.al)

- Practitioner guidance on opening customer entries (search snippet): post each entry "with the customer on one side and the customer's receivables account" as balancing account; "Document type should be Invoice for an open entry, or Credit Memo for a credit entry"; G/L nets to zero on the receivables account while open customer ledger entries are created — [usedynamics.com: Customer opening entries](https://usedynamics.com/business-central/details/customer-opening-entries/)

### Inferences
- Recommended design (derived): one AL app with (a) `page 50100 "Opening Journal Lines"` — `PageType = API; APIPublisher='yourco'; APIGroup='migration'; APIVersion='v1.0'; EntityName='openingJournalLine'; EntitySetName='openingJournalLines'; SourceTable="Gen. ## Key Question 4: Custom AL API pages, codeunit unbound actions, S2S auth, permission sets, Entra app setup

### Takeaway
S2S = Entra app registration with **Application** permission `API.ReadWrite.All` (plus `Automation.ReadWrite.All` only for `/api/microsoft/automation`), admin consent, token from `https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token` with scope `https://api.businesscentral.dynamics.com/.default`, and a **Microsoft Entra Applications** record in each BC environment (State = Enabled, permission sets assigned; SUPER not allowed). Codeunit procedures are exposed as `POST /ODataV4/{ServiceName}_{Procedure}?company=...` after publishing on the Web Services page (or via a `TenantWebServiceCollection` XML shipped in the extension).

### Cited Findings
- Entra app: register (single- or multi-tenant); redirect URI optional (`{webclient}/OAuthLanding.htm`, only needed to grant consent from the BC client); create client secret; **API permissions → Microsoft APIs → Dynamics 365 Business Central → Application permissions**: `API.ReadWrite.All` ("access to APIs and web services") and `Automation.ReadWrite.All` ("full access to automation APIs"); optionally Grant admin consent in the portal — [Using S2S authentication](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/automation-apis-using-s2s-authentication)

MGT. - ADMIN** provide access to most typical objects used with automation"; optional **Grant Consent** action (needs the redirect URL) — [Using S2S authentication](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/automation-apis-using-s2s-authentication)
- Token request (client credentials): `POST https://login.microsoftonline.com/{{tenantId}}/oauth2/v2.0/token` with `grant_type=client_credentials&client_id=...&client_secret=...&scope=https://api.businesscentral.dynamics.com/.default`; then `GET https://api.businesscentral.dynamics.com/v2.0/{env}/api/v2.0/companies` with `Authorization: Bearer ...` — [Using S2S authentication](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/automation-apis-using-s2s-authentication)

- Third-party connector guidance (search snippets, not Microsoft): Jitterbit recommends **D365 BUS FULL ACCESS** for the Entra application ("minimum acceptable is D365 COMPANY HUB"); others suggest **D365 FULL ACCESS** — [Jitterbit BC v2 prerequisites](https://docs.jitterbit.com/integration-studio/design/connectors/microsoft-dynamics-365-business-central-v2/prerequisites/)
- Protect tokens in AL with `[NonDebuggable]` and `showMyCode = false`; Microsoft's REST Client sample lives in BCTech `samples/VSCRestClientOAuthBCAccess` — [Using S2S authentication](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/automation-apis-using-s2s-authentication)

### Inferences
- For an ASP.NET Core (.NET 10) backend: use `Microsoft.Identity.Client` (`ConfidentialClientApplicationBuilder.Create(clientId).WithClientSecret(...).WithAuthority(AzureCloudInstance.AzurePublic, tenantId)` → `AcquireTokenForClient(new[]{"https://api.businesscentral.dynamics.com/.default"})`) or a plain `HttpClient` form-post to the token endpoint; cache the token (~1h lifetime) and pre-emptively refresh. Only one Entra app permission (`API.ReadWrite.All`) is needed for `/api/v2.0`, custom `/api/{publisher}/{group}/{version}` and `/ODataV4` routes; add `Automation.ReadWrite.All` only if you also drive configuration packages (KQ5).
- Permission sets for the Entra application record (derived): for posting general journals the application needs read/insert/modify/delete on `Gen. Journal Batch`/`Gen. Journal Line` and execute on the posting codeunits plus insert on ledger tables. A pragmatic choice is `D365 BUS FULL ACCESS` (business data without setup/admin) or a custom permission set composed of the standard `D365 JOURNALS, EDIT` + `D365 JOURNALS, POST` style sets plus your extension's objects; test in the QA sandbox because the posting codeunits touch many tables. The MS doc's `D365 AUTOMATION` / `EXTEN. MGT. - ADMIN` recommendation targets automation/tenant-setup scenarios, not journal posting.
- One Entra app registration can serve both sandbox and production (same client ID), but a **Microsoft Entra Applications** record must exist in each BC environment (it is environment/tenant data); the token is tenant-wide, the environment is chosen by the URL.

### Gaps
- No Microsoft document enumerates the exact permission set(s) required for posting general journals through S2S; "D365 BUS FULL ACCESS" appears only in third-party connector guides. The exact minimal set needs empirical validation.
- The S2S doc still says "For most cases, use the `AcquireTokenByAuthorizationCode` method" in its sample section, which contradicts the client-credentials flow it describes; treat as a doc inconsistency.

## Key Question 6: Rate limits, throttling, `$batch`, payload sizes, ETag/If-Match, deep insert, headers

### Takeaway
Per-user (incl. service principal) limits: 6 000 OData requests per 5-minute sliding window, 5 concurrent, 100 simultaneous connections (95 queued), 8-minute operation timeout (408), 10-minute request limit (504), 350 MB max body, 20 000 max page size, **max 100 operations per `$batch`**; `$batch` with `Isolation: snapshot` makes all inner requests one transaction; PATCH/DELETE require `If-Match` (ETag or `*`); deep insert works on API pages (journals → journalLines → dimensionSetLines) but deep PATCH does not.

### Cited Findings
- OData per-user limits: "Max concurrent requests … 5" (excess queued, 503 after 8 min), "Max connections … 100" (429 when exceeded), "Max request queue size … 95" (429), "Speed (rate) … within a 5-minute sliding window … 6000" (429); per-environment table: "Max body size 350 MB", "Max page size 20,000" (413), "**Max batch size** The maximum number of operations in an OData V4 $batch request. 100", "Operation timeout … 8 minutes" (408); per-user limits "rolled out gradually starting in late December 2023"; "Are limits applied differently for application users (service principals)? No."; spread load "in a round-robin fashion or rotation through a list of users or service principals" — [Operational limits for Business Central online](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/operational-limits-online)
- Historic per-environment rate was Sandbox 300 / Production 600 requests per minute (now per-user) — [Operational limits](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/operational-limits-online)
- "An HTTP Status Code 429 will be returned when throttling occurs" → retry with cool-off (fixed, incremental, exponential back-off, randomization); "Request execution time is limited to 10 minutes … `504 - Gateway Timeout`"; recommendations: webhooks, batching ("If the batch is too large, a timeout occurs"), `$filter`, `$expand`, deep inserts ("Deep insert can also be performed in Batch calls") — [Working with API limits](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/dynamics-rate-limits); [Current API limits](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/dynamics-current-limits)
- Transactional `$batch` (v17.1+): `POST businesscentralPrefix/api/v2.0/$batch`, headers `Authorization`, `Content-Type: application/json` ("Required for JSON Batch content"), `Accept: application/json`, `Isolation: snapshot`; body `{"requests":[{"method":"PATCH","url":"items(7ce0af2e-...)","headers":{"Company":"CRONUS International Ltd.","Content-Type":"application/json","If-Match":"*"},"body":{...}}, ...]}`; "Unless it's invoked commit, if an inner request fails after another request(s) has committed changes, all changes within a batch will be reverted"; "makes the entire batch to run within the same session. If the AL code doesn't invoke COMMIT, then the entire batch runs in the same transaction"; `CommitBehavior` attribute can override; response is `{"responses":[{"id":null,"status":200,...},{"status":204},{"status":400,"body":{"error":{"code":"Unknown","message":"... CorrelationId: x."}}}]}` — [Using OData transactional $batch requests](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/use-odata-batch)
- "PATCH operations require the 'If-Match' header to be set, either with a retrieved ETag or with '*'." — [Using OData to modify data](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/use-odata-to-modify-data)
- "Business Central supports deep insert on API page types. It's not supported on pages exposed as ODataV4 web services"; "doesn't support deep patching"; `OR` across different fields not supported in `$filter`; lambda operators ignored; PATCH of collection properties impossible — [Known OData limitations](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/odata-known-limitations)
- Other useful headers: `Accept-Language` (controls error-message language and date/number formatting), `Data-Access-Intent: ReadOnly|ReadWrite` (modification requests only accept ReadWrite; `OPTIONS` may advertise fewer methods under ReadOnly) — [Tips for working with APIs](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-connect-apps-tips)
- Known issue KA-24233 (search snippet): "Journal Line API responses can be inaccurate when large batches are processed … two transactions in one batch are assigned the same line number, so one is recorded and the other fails with a duplicate line number error … exacerbated when large batches (e.g., 2k to 30k transactions) are processed"; workaround: avoid concurrent processing, pause between batch requests — [KA-24233](https://community.dynamics.com/article/KA-24233)
- Community (search snippet): Demiliani's per-user description: 5 concurrent, 100 simultaneous (processed + queued), 6000 per 5-minute window, ~500 parallel calls per NST — [demiliani.com (Nov 2024)](https://demiliani.com/2024/11/29/how-dynamics-365-business-central-handles-incoming-web-service-calls-for-dummies/)
- A community client verified a three-level deep insert `journals` → `journalLines` → `dimensionSetLines` in one POST and noted `dimensions` (v1-style) property is rejected — [uptick/pybusinesscentral PR #18](https://github.com/uptick/pybusinesscentral/pull/18)

### Inferences
- Practical batch design for the standard API (derived): one `$batch` with `Isolation: snapshot` containing up to **99 `POST journals({id})/journalLines` inner requests + 1 `POST journals({id})/Microsoft.NAV.post`** (≤100 total) makes "create lines and post" atomic: if posting fails, the lines are rolled back and the batch stays empty. Inner request URLs are relative to the `/api/v2.0/` root (`companies({id})/journals({id})/journalLines`), each inner request must carry `Content-Type: application/json`, and the `Company` header is optional when the company is in the URL. Alternatively a single **deep insert** `POST journals` with `journalLines: [...]` creates batch + lines in one request (no 100-op ceiling, but then the post is a separate call and not transactional with the insert unless wrapped in a `$batch`).
- Serialize journal-line creation per batch (no parallel POSTs into the same batch) to avoid the KA-24233 duplicate-`Line No.` race; use one journal batch per logical unit (e.g. `OB-CUST-01`) and sequential `lineNumber` values (10000, 20000, …) supplied explicitly.
- Keep each `$batch` small enough to finish well under 8 minutes (posting ~100 lines is seconds, but customer/vendor lines with currency and VAT are slower than G/L lines).
- Implement 429/503 handling with exponential back-off + jitter and honour `Retry-After` if present; cap concurrency at ≤5 per service principal.

### Gaps
- No Microsoft documentation of a `Retry-After` header on 429 responses was found in the reviewed pages.
- Whether `Microsoft.NAV.post` inside a snapshot `$batch` is rolled back when a *later* inner request fails depends on the posting codeunit not committing; `Gen. Jnl.-Post Batch` does commit internally in some paths (not verified here), so put the post action **last** in the batch.

### Inferences
- Idempotency recipe (derived): (1) generate a deterministic `documentNumber` per opening document (e.g. `OB-C10000-INV1001`, ≤20 chars) and put the legacy key in `externalDocumentNumber` (≤35 chars); (2) before creating lines, `GET companies({id})/generalLedgerEntries?$filter=documentNumber eq 'OB-…'&$top=1` — if found, the batch already posted; (3) also `GET journals({id})/journalLines` — if lines exist unposted, delete or reuse them; (4) create lines + post inside one snapshot `$batch`; (5) on 408/504/timeouts, re-run step 2 before retrying. Because document numbers may be renumbered by the batch's Posting No. Series, either leave the batch's `No. Series`/`Posting No. Series` blank for migration batches or key the check on `externalDocumentNumber`, which `generalLedgerEntry` does **not** expose — so for G/L verification use `documentNumber`, and for customer/vendor verification build a custom read-only API page/query over `Cust. Ledger Entry` (table 21) / `Vendor Ledger Entry` (25) exposing `documentType`, `documentNo`, `externalDocumentNo`, `customerNo`, `amount`, `remainingAmount`, `dueDate`, `open`.
- Dimensions on standard journal lines: POST `.../journals({jid})/journalLines({lid})/dimensionSetLines` with `{"code":"DEPARTMENT","valueCode":"ADM"}` per dimension (one request each, or nested in a deep insert); default dimensions of the account/customer/vendor are applied automatically when `Account No.` is validated (standard `CreateDim` behaviour; validation errors for `Code_Mandatory` default dimensions surface at posting as `Application_DialogException`).
- Pre-flight checks to avoid the most common failures: G/L Setup / User Setup **Allow Posting From/To** must cover the opening date (note: the S2S application account is a *user* and can have its own User Setup row); balancing G/L accounts must have `Direct Posting = Yes` (if you balance against the receivables control account directly, it is normally `Direct Posting = No`, so the typical pattern is to let the customer posting group hit it indirectly and balance against an opening-balance suspense account); customer/vendor must have Posting Group and Payment Terms; blocked dimension combinations.

### Gaps
- No standard endpoint for customer/vendor ledger entries or remaining amounts exists in v2.0 (`customerFinancialDetail` gives only balance/overdue totals); confirmed by the resource list but not tested.
- Exact text of the `TestField("Direct Posting")` message comes from the platform (`"Direct Posting must be equal to 'Yes' in G/L Account: No.=…"`); the literal was not seen in a reviewed source.

## Key Question 8: Testing — sandbox vs production naming, company id resolution, journal id discovery, environment list

### Takeaway
Environment name goes in the URL (`/v2.0/{tenantId}/QA-AGI/api/v2.0/...`); resolve the company GUID with `GET .../companies`, then the journal batch GUID with `GET .../companies({id})/journals?$filter=code eq 'OPENBAL'` (listing defaults to the GENERAL template), or create the batch via `POST journals`; the same Entra app works in sandbox and production as long as a Microsoft Entra Applications record with the right permission sets exists in each environment.

### Cited Findings
- Endpoint forms: common `https://api.businesscentral.dynamics.com/v2.0/<environment name>/api/v2.0` (e.g. `.../v2.0/production/api/v2.0`) and direct-tenant `https://api.businesscentral.dynamics.com/v2.0/<user domain name or tenant id>/<environment name>/api/v2.0` (e.g. `.../v2.0/cronus.com/sandbox/api/v2.0`); "the name of the environment being connected to needs to go into the URI" — [Endpoints for the APIs](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/endpoints-apis-for-dynamics)
- Listing environments on the tenant: `GET https://api.businesscentral.dynamics.com/environments/v1.2` — [Getting a list of environments](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/api-get-environments)
- Company id: "All resources live in the context of a parent company, which means that the company ID must be provided in the URL for all resource API calls", e.g. `GET <endpoint>/companies` → `{"value":[{"id":"a0a0a0a0-...","systemVersion":"18453","name":"CRONUS USA, Inc.","displayName":"CRONUS USA, Inc."}]}` then `<endpoint>/companies(a0a0a0a0-...)/customers` — [Tips for working with APIs](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-connect-apps-tips)
- Company can be given "as part of the URL or as a query parameter" — [API endpoint structure](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/api-endpoint-structure)
- `GET journals` without a template filter returns batches of the default general template; `GET journals({id})` works by SystemId regardless of template — [APIV2Journals.Page.al](https://github.com/microsoft/BCApps/blob/main/src/Apps/W1/APIV2/app/src/pages/APIV2Journals.Page.al)
- Sandbox-vs-production checklist: same user exists and is active in both; same entitlements and permissions; pages/codeunits exposed the same way; extensions' **Allow HttpClient Requests** set the same — [Troubleshooting web services: It works in my sandbox but not in production](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/web-service-troubleshooting)
- Transition notes: v2.0 keys are always `SystemId` GUIDs ("It's also possible to create a new record and provide the SystemId in API v2.0"); complex/nested v1.0 properties (e.g. `dimensions` collections) were replaced by first-level properties/navigation — [Transitioning from API v1.0 to v2.0](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/transition-to-api-v2.0)
- BC Online authentication for APIs is Microsoft Entra ID only; basic auth with web-service access keys is listed only for on-premises — [Endpoints for the APIs](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/endpoints-apis-for-dynamics)

### Inferences
- For `Bc__Environment = "QA-AGI"`: base URL `https://api.businesscentral.dynamics.com/v2.0/{tenantId}/QA-AGI/api/v2.0`; custom API `https://api.businesscentral.dynamics.com/v2.0/{tenantId}/QA-AGI/api/{publisher}/{group}/{version}`; unbound action `https://api.businesscentral.dynamics.com/v2.0/{tenantId}/QA-AGI/ODataV4/{Service}_{Proc}?company={companyId}`. Environment names are case-insensitive in practice but keep the exact admin-center spelling; URL-encode spaces.
- Journal id discovery flow: `GET journals?$filter=code eq 'OPENBAL'` → if empty `POST journals {"code":"OPENBAL","displayName":"Opening balances","balancingAccountNumber":"9999"}` (code ≤10 chars, uppercase) → cache the returned `id` per environment+company. Because v2.0 allows client-supplied `id`, a deterministic GUID per environment can be supplied on create for idempotent setup.
- Use `$select`/`$top=1` on verification reads and `Data-Access-Intent: ReadOnly` for pure reads (not on the post call).

### Gaps
- Whether the environment name in the URL is case-sensitive was not found in documentation.
- The `environments/v1.2` listing endpoint's required token scope/permissions were not reviewed (different route from `/api/v2.0`).
