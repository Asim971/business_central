## Key Question 1 — What exactly does the usedynamics "Customer Opening Entries" article recommend (journal, account type, document type, per-invoice vs lump sum, balancing account, dates, document no., dimensions, currency, posting-group effect)?

### Takeaway
The usedynamics method is: a **dedicated General Journal batch**, **one line per open customer document** (Account Type = Customer, Document Type = Invoice or Credit Memo, original document number), **balanced against the very same Receivables Account that the Customer Posting Group points to**, so the G/L nets to zero and only the Customer Ledger Entries remain; G/L balances are then loaded last in a separate zero-total journal. Note that this is *not* a separate "opening-balance clearing account" method — that variant comes from other sources (see KQ2).

### Cited Findings
- The customer guide "recommends a dedicated general journal batch, with the customer on one line and the receivables account as the balancing account. Set the document type to Invoice for normal entries and Credit Memo for credit entries, and enter the original posted document number so you can trace it back." It adds that "the receivables account is found through the customer posting group, where the receivables account is defined." — [usedynamics: How to create Opening Entries for the Customers](https://usedynamics.com/business-central/details/customer-opening-entries/) (via search snippet)
- Rationale as stated by the article: posting each open entry with the customer on one side and the customer's receivables account as the balancing account "nets the general ledger to zero while still creating open customer ledger entries you can apply payments against later"; "This nets the general ledger to zero, so your open entries appear in the customer ledger without affecting the chart of accounts." — [usedynamics customer article](https://usedynamics.com/business-central/details/customer-opening-entries/) (via search snippet)
- Sibling page on the posting-group mechanism: "The Customer Posting Groups determines the Receivables Account". — [usedynamics: Customer Posting Groups](https://usedynamics.com/business-central/finance/customer-posting-groups/)
- The vendor article (mirror of the customer one) "describes using a general journal... For each line, you enter the document number from the old system, the vendor account, an external document number from the vendor invoice, the currency, the amount, and any dimensions such as project code." The page is "roughly six years old" per the search summary. — [usedynamics: How to create Opening Entries for the Vendors](https://usedynamics.com/business-central/details/vendor-opening-entries/) (via search snippet)
- Series-level sequencing: "post subledger openings (customers, vendors, VAT, bank) first, with inventory done through the item journal before the G/L. The final step is a general ledger opening journal that must balance to zero in total." Mid-period go-live: "revenue and cost accounts also need to be posted so the G/L reflects activity already in the period." The strategy article is "about seven years old". — [usedynamics: A Strategy for Opening Balances](https://usedynamics.com/business-central/details/opening-balances-strategy/) (via search snippet)
- Microsoft confirms the posting-group mechanism the article relies on: "Posting with a general journal creates entries on general ledger accounts. Entries are created even when, for example, you post a journal line to a customer account, because an entry is posted to a general ledger receivables account through a posting group." — [Microsoft Learn: Post transactions directly to the general ledger](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-post-transactions-directly) (repo source `finance-how-post-transactions-directly.md`, ms.date 10/03/2025)
- Debit/credit convention for journal lines: "A positive amount in the **Amount** field is debited to the main account and credited to the balancing account. A negative amount is credited to the main account and debited to the balancing account." — [Microsoft Learn: Work with general journals](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-work-general-journals) (repo source, ms.date 04/07/2026)

### Inferences
- Field-by-field recipe for a customer opening line in **General Journals** (page 39), as implied by the sources above: Posting Date = cut-over date; Document Type = Invoice (positive Amount) or Credit Memo (negative Amount); Document No. = legacy invoice number; External Document No. = customer's reference if any; Account Type = Customer; Account No. = customer; Amount = open (remaining) amount in the document's currency with Currency Code set; Due Date = legacy due date (override whatever payment terms compute, because ageing must match the legacy aged list); Bal. Account Type = G/L Account; Bal. Account No. = the receivables account from the customer's posting group (usedynamics/MB-800 pattern) or a clearing account (KQ2 alternative); dimensions as per legacy.
- Because every line's Bal. Account is the same receivables control account that the posting group will hit, the net G/L effect of the whole batch is exactly zero and the receivables control is subsequently populated by the G/L trial-balance journal (KQ3). The only residual is the set of open Customer Ledger Entries.
- Negative-amount lines (credit memos / unapplied payments) should be posted with Document Type = Credit Memo (or Payment) so later application in the Cash Receipt Journal / Apply Entries behaves like native documents.

### Gaps
- The customer article's exact statements about posting date (e.g., "day before go-live"), due date, dimensions and currency could not be verified because the page could not be fetched; the vendor snippet confirms currency, dimensions and external document no. are entered, and the sequence pages imply the opening date, but no quoted text exists for the customer page on these points.
- Whether usedynamics mentions the **Direct Posting** flag at all is unknown (nothing in snippets).

## Key Question 2 — Why a dedicated "Opening Balance"/clearing account (or the control account itself) as balancing account, how it nets to zero, and why the receivables control should have Direct Posting = No

### Takeaway
Two equivalent techniques exist: (A) balance sub-ledger lines to the **control account itself** (usedynamics, MB-800 lab) so each sub-ledger batch is G/L-neutral; or (B) balance them to a **migration clearing/suspense G/L account**, then post the legacy trial balance with the control accounts and the *same* clearing account on the other side so that the clearing account ends at zero. Method B is favoured by several consultants because reversing a single bad line never leaves the control account out of step with the sub-ledger. Keeping **Direct Posting = No** on control accounts (AR/AP/bank/inventory) afterwards is standard practice and Microsoft explicitly recommends it for bank posting-group accounts.

### Cited Findings
- Technique A rationale (control account as balancing account): "The GL entries cancel out to zero on that account, while the open customer ledger entries are created with the correct amounts." — [usedynamics customer article](https://usedynamics.com/business-central/details/customer-opening-entries/) (via search snippet)
- Technique A in Microsoft's MB-800 lab: CUST batch "Bal. Account No. 10400", VEND batch "Bal. Account No. 20100"; "The total amount will be balanced by the regular g/l accounts for accounts receivables (10400) and accounts payable (20100)." — [MB-800 Lab 09](https://microsoftlearning.github.io/MB-800-Business-Central-Functional-Consultant/Instructions/Labs/Lab09_Set_up_General_Journals.html)
- Technique B (suspense/clearing): "Method 1 balances entries to the Accounts Receivable control account, but can cause issues if a balance is reversed. Method 2 balances to a Suspense Code and then reverses the balance to the Accounts Receivable GL Code, mitigating the risk of imbalance." — [thedynamicsexplorer, Sales & Purchase Ledger opening balances (9 May 2024)](https://thedynamicsexplorer.com/2024/05/09/dynamics-365-business-central-a-couple-of-methods-i-use-when-posting-opening-balances-for-sales-and-purchase-ledger/)
- Technique B as taught for MB-800: "Subledger journal entries automatically post to G/L control accounts (AR/AP) via posting groups and must be balanced against the Migration Clearing account to offset the initial trial balance and eliminate double-counting." — [open-exam-prep 1.3](https://open-exam-prep.com/study-guides/mb-800/company-creation-migration/opening-balances-migration)
- Microsoft's bank-account guidance describes the same clearing logic generically: "Usually, you post the opening bank balance directly to the bank account, and the amount ends up in the G/L account. Alternatively, later you can reverse it out of the G/L account you use to balance the opening general ledger balance." — [Microsoft Learn: Set up bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/bank-how-setup-bank-accounts) (repo source)
- Direct Posting recommendation from Microsoft (bank context): "Define the general ledger accounts that bank account entries are posted to... We recommend that these G/L accounts have the **Direct Posting** field set to *No*." — [Microsoft Learn: Set up posting groups](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-posting-groups) (repo source `finance-posting-groups.md`)
- Why: "Direct posting breaks the connection between the bank account ledger entry and the G/L account ledger entry. When you reconcile your bank account, the entries posted directly to the G/L account aren't included... This mistake often happens when entering an opening balance for a bank account." — [Microsoft Learn: Reconcile bank accounts, "Avoid direct posting"](https://learn.microsoft.com/en-us/dynamics365/business-central/bank-how-reconcile-bank-accounts-separately#avoid-direct-posting) (repo source)
- Partner guidance extends the rule to AR: Direct Posting is a G/L account card field that blocks posting straight to subledger-controlled accounts; "Turn Direct Posting Off For: Accounts Receivable control accounts." — [Dynamics Power Play: Direct Posting in Business Central](https://dynamicspowerplay.com/direct-posting-in-business-central-the-tiny-setting-that-prevents-massive-accounting-headaches/); "Accounts such as inventory, accounts payable, accounts receivable, and bank balances should typically be updated only through their respective submodules." — [ERP Software Blog: Managing Direct Posting (Nov 2025)](https://erpsoftwareblog.com/2025/11/managing-direct-posting-in-business-central-enabling-control-without-disruption/)
- Built-in check that the control = sub-ledger relationship holds: report **Reconcile Cust. and Vend. Accs** (ID 33) — "Check whether customer and vendor ledger entries balance with corresponding general ledger entries." — [Microsoft Learn: Prepare to close statements](https://learn.microsoft.com/en-us/dynamics365/business-central/year-prepare-close-statement) (repo source)

### Inferences
- Netting arithmetic, Technique B: Customer batch posts Dr Receivables (via posting group) / Cr OPENING-CLEARING for Σ open invoices. The G/L trial-balance batch then posts the legacy *Receivables* balance as Dr OPENING-CLEARING / Cr ... — i.e., the receivables line of the trial balance is entered **against the clearing account instead of against the control account**. After both batches: Receivables = legacy balance (from the sub-ledger lines only), OPENING-CLEARING = 0, and every other G/L account = legacy balance. If OPENING-CLEARING is not zero, the legacy aged list and the legacy trial balance did not reconcile.
- Netting arithmetic, Technique A: Customer batch posts Dr Receivables / Cr Receivables for every line (via posting group and via Bal. Account), so G/L is untouched; the receivables balance is then supplied by the trial-balance journal. The risk is that a *Reverse Transaction* of one line also reverses a G/L entry on the control account, while the trial-balance line stays — which is exactly the imbalance thedynamicsexplorer describes.
- Direct Posting must be temporarily **Yes** on the control account under Technique A (because the Bal. Account line posts directly to it) and on the clearing account under Technique B; it should be set back to **No** on AR/AP/bank/inventory control accounts immediately after cut-over. (No Microsoft page documents the G/L Account Card "Direct Posting" field itself in the current repo — see Gaps.)

### Gaps
- No current Microsoft Learn how-to page in the docs repo documents the **Direct Posting** field on the G/L Account Card (only the bank posting-group recommendation was found); the AR-specific recommendation rests on partner blogs.
- I found no source quantifying how often Technique A actually causes problems; thedynamicsexplorer calls it "uncommon".

## Key Question 3 — G/L opening balances: trial-balance import via General Journal, posting date, retained earnings / income-statement treatment, Close Income Statement, VAT avoidance

### Takeaway
Load the G/L as a self-balancing General Journal (Account Type = G/L Account on every line, no Bal. Account, journal total = 0), posted **last**, after every sub-ledger batch has been reconciled, typically dated the day before go-live (or prior year-end for a year-start go-live, optionally followed by monthly net-change journals). The journal must carry **no VAT**: leave Gen. Posting Type and the VAT Bus./Prod. Posting Groups blank (and clear "Copy VAT Setup to Jnl. Lines" on the batch/template) so no VAT Entries are created. Prior-year P&L should arrive as retained earnings (or be closed with Close Income Statement if full prior-year P&L detail is loaded).

### Cited Findings
- usedynamics G/L method: "posting the GL opening in a general journal, with the chart of accounts net change at zero beforehand and the journal totaling zero with no balancing account on each line"; "Subledger openings, including VAT, offset each other, so the net change stays at zero until the general ledger opening entries are posted"; "the GL opening is typically the last opening you post, and... the journal must balance to zero in total." — [usedynamics: How to create an Opening Balance in the General Ledger](https://usedynamics.com/business-central/details/gl-opening-balance/) (via search snippets)
- Mid-period go-live: "when a company goes live mid-period, revenue and cost accounts also need to be posted so the G/L reflects activity already in the period." — [usedynamics strategy article](https://usedynamics.com/business-central/details/opening-balances-strategy/) (via snippet)
- Microsoft's configuration-package route for G/L opening balances: run **Create G/L Acct. Journal Lines** (lines created with empty amounts) → export the journal table to Excel and enter the posting and balancing account information from legacy data → re-import/apply → in the configuration worksheet select the journal-line table, choose **Database Data**, review, then **Post**; "The G/L account steps also apply to customer, vendor, and item journals"; explicit warning: "do not follow the steps in this article to post directly to the G/L accounts that are associated with the relevant bank accounts." — [Microsoft Learn: Apply company configuration packages](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/apply-company-configuration-packages) (read from GitHub raw source of `dynamics365smb-devitpro-pb`)
- Default configuration package contents include **Gen. Journal Line** and **Item Journal Line** among its 27 tables; "Working with configuration packages is advanced functionality, and we recommend that you contact your reselling partner." — [Microsoft Learn: Import business data from other finance systems](https://learn.microsoft.com/en-us/dynamics365/business-central/across-import-data-configuration-packages) (repo source)
- Posted ledgers are not importable: "Customer Ledger Entries, Vendor Ledger Entries, Item Ledger Entries, and G/L Entries are all protected", so staging goes through Gen. Journal Line (table 81) and posting. — [knowledgelib: Business Central RapidStart (2026)](https://knowledgelib.io/business/erp-integration/business-central-rapidstart/2026); see also [yzhums: use Configuration Package to post General Journal](https://yzhums.com/16530/)

- Another consultant names the batch **OPENBAL-GL**, loads it via configuration package, and "right after posting the opening balance journal, I print and save a copy of the General Ledger Trial Balance and notes the G/L Register entry." — [thedynamicsexplorer: How I post opening balances for the General Ledger (11 Jun 2024)](https://thedynamicsexplorer.com/2024/06/11/dynamics-365-business-central-how-i-post-opening-balances-for-the-general-ledger-in-business-central/)
- Close Income Statement mechanics: "This job transfers the year's result to an account in the balance sheet and closes the income statement accounts... creating lines in a journal, which you then can post... you must specify a balancing account and retained earnings account in the balance sheet before you post... The date on the lines... is always a closing date for the fiscal year... a fictitious date between the last day of the old fiscal year and the first day of the new year." - VAT itself is handled as its own sub-ledger opening (so that the first BC VAT return is complete): post the open VAT via a General Journal "with the VAT business and product posting group combination, and Business Central calculates the VAT. The same VAT account serves as both posting and balancing account, so the general ledger stays at zero. Reverse-charge combinations... post to a different account, so you need a separate manual journal entry to clear that deviation." — [usedynamics: How to create Opening Entries for the VAT](https://usedynamics.com/business-central/details/vat-opening-entries/) (via snippet); same approach for mid-period go-live — [thedynamicsexplorer: VAT opening balances mid-VAT period (14 Oct 2024)](https://thedynamicsexplorer.com/2024/10/14/dynamics-365-business-central-a-method-for-posting-vat-opening-balances-when-going-live-mid-vat-period/)

### Inferences
- Recommended G/L batch shape (BC Online 2025–2026): General Journal Template **OPENING** (Type General, Force Doc. Balance off, Copy VAT Setup to Jnl. Lines off), batch **BALANCE**/**OPENBAL-GL**, one Document No. for the whole journal (so Force Doc. Balance would otherwise require each document to balance — it does, as the journal sums to zero), every line Account Type = G/L Account, Gen. Posting Type / VAT groups blank, Bal. Account No. blank, dimensions filled where the legacy TB is dimensioned.
- Treat the receivables/payables/bank/inventory lines of the trial balance according to the technique chosen in KQ2: under Technique B they are posted against the clearing account (so the clearing account zeroes); under Technique A they are posted normally (direct posting to the control account must be temporarily allowed).
- If the go-live is at fiscal year start, load the closing balance sheet (with prior-year result already in retained earnings) dated the last day of the prior year, and consider the **closing date** (`C31-12-YYYY`) only if you also load P&L detail and intend to run Close Income Statement in BC; otherwise P&L accounts of the prior year are not loaded.

## Key Question 4 — Vendor opening entries (mirror of customers)

### Takeaway
Vendors are loaded exactly like customers: General Journal, Account Type = Vendor, one line per open purchase invoice/credit memo with Document Type = Invoice/Credit Memo, legacy document number, **External Document No.** = the vendor's invoice number, currency, due date, dimensions; Bal. - Per-invoice lines with due dates for vendors: "the vendor invoice number and due date for vendor lines." — [aguidetocloud MB-800 data migration](https://www.aguidetocloud.com/guided/mb-800/domain-1/data-migration/)

### Inferences
- A vendor invoice line posted from the General Journal with Document Type = Invoice and a filled External Document No. satisfies the "Ext. Doc. No. Mandatory" check in Purchases & Payables Setup if it is on, and gives the AP team the vendor reference for remittance matching.
- Posting Date drives ageing when the Aged Accounts Payable report is run by posting date; Due Date must be keyed per line because the vendor's Payment Terms would otherwise recompute it from the (cut-over) posting/document date.

### Gaps
- The vendor article's exact balancing-account wording was not visible in snippets ("The vendor page doesn't say which balancing account to use"); the payables-control approach is inferred from the customer article and the MB-800 lab.

## Key Question 5 — Bank accounts, inventory (Item Journal Positive Adjmt. + cost posting), fixed assets (FA journal with acquisition cost and accumulated depreciation)

### Takeaway
Bank: post the opening balance to the **Bank Account** (Account Type = Bank Account) — never directly to its G/L account — and balance it against the clearing account/G/L opening; reconcile any direct G/L posting before the first bank reconciliation. Inventory: **Item Journal**, Entry Type **Positive Adjmt.**, per item/location(/lot/serial) with Unit Amount = legacy unit cost (standard-cost items take the item-card standard cost); with Automatic Cost Posting (default on) this debits the **Inventory** account and credits the **Inventory Adjmt.** account of the General Posting Setup, so the inventory line of the trial balance must be entered against the Inventory Adjmt./clearing account. Fixed assets: turn **G/L Integration off** on the depreciation book, post per asset in the **Fixed Asset Journal** an acquisition-cost line plus accumulated-depreciation lines (to prior year-end, and current-year to date), then turn integration back on; the G/L side comes from the trial-balance journal.

Posting dates of the FA lines should be the legacy acquisition date / prior year-end / cut-over date respectively so the depreciation calculation starts correctly.

### Takeaway

### Inferences
- Reconciliation checklist in order: (1) after each sub-ledger batch, Chart of Accounts → Net Change filtered to the cut-over date = 0 (Technique A) or clearing-account balance = Σ expected control balances (Technique B); (2) Reconcile Cust. and Vend. ## Consolidated step-by-step cut-over sequence (synthesis of all cited sources; see each KQ for citations)

1. **Prepare** (legacy): apply all payments/credits in the source system; export aged AR/AP (open items with doc no., ext. doc no., dates, due dates, currency, remaining amount, dimensions), bank book balances reconciled to statement, inventory count with unit costs by location/lot, FA register (cost, accumulated depreciation to prior FYE and YTD), VAT open entries, trial balance (and monthly net changes if history wanted).
2. **BC setup**: chart of accounts (control accounts' Direct Posting = No; an "OPENING BALANCE CLEARING" G/L account with Direct Posting = Yes if using Technique B), posting groups, dimensions, number series, Inventory Setup (Automatic Cost Posting), depreciation books with G/L integration OFF, General Ledger Setup / User Setup Allow Posting From/To covering the cut-over date, General Journal Template OPENING (Force Doc. Balance off, Copy VAT Setup to Jnl. Lines off) with batches CUST / VEND / BANK / VAT / BALANCE.
3. **Dry run** in a copied/sandbox company; confirm Chart of Accounts net change = 0 and ledgers empty before each live batch.
4. **Post sub-ledgers** (all dated the cut-over date, e.g., day before go-live): Bank (Account Type = Bank Account); Customers (one line per open document, Document Type Invoice/Credit Memo, legacy Document No., Due Date, Currency, dimensions, Bal. Account = receivables control or clearing); Vendors (same with External Document No.); VAT (General Journal with VAT posting groups, VAT account both sides); Inventory (Item Journal, Positive Adjmt., Unit Amount = cost, per item/location/lot); Fixed assets (FA Journal: acquisition cost + accumulated depreciation lines per asset, integration off, then turn integration on).
5. **Reconcile each sub-ledger** to its control account / to the legacy report before continuing.
6. **Post the G/L trial balance** (General Journal, Account Type = G/L Account, zero total, no VAT); control-account lines go against the clearing account (Technique B) so the clearing account ends at 0; use retained earnings for prior-year P&L or load P&L detail and run Close Income Statement.
7. **Prove**: Detail Trial Balance / Trial Balance Excel = legacy TB; Reconcile Cust. and Vend. Accs; Aged AR/AP (by due date) = legacy aged; Customer/Vendor Balance to Date; Inventory Valuation = Inventory G/L and Inventory - G/L Reconciliation = 0; first bank reconciliation with no direct-posting warning; FA book values; VAT Statement preview = VAT G/L accounts; save Trial Balance and note G/L Register no.
8. **Lock down**: set Direct Posting = No on control accounts, restore Allow Posting From/To windows, block the OPENING batches.
9. **Correct** mistakes with Reverse Transaction (journal-originated, unapplied, once) or offsetting lines; unapply first if applied; inventory value via Revaluation Journal.
