Scope note: Research was done 2026-10-11 against the current Microsoft Learn source (MicrosoftDocs/dynamics365smb-docs and dynamics365smb-devitpro-pb, `main` branch, page dates 2024–2026) plus partner/community material surfaced via web search. ## Key Question 1 — Sequence and avoiding double counting of control accounts

### Takeaway
Microsoft's own guidance is "setup → master data → opening balances via journals", with G/L balances first, then open customer entries, then open item ledger entries; the practical consensus (study guides, partner tool vendors) is to post the G/L trial balance against a migration clearing/suspense account and then post sub-ledger detail (customer, vendor, bank, inventory, FA) against the same clearing account so the control accounts are populated **only** by the sub-ledger postings and the clearing account nets to zero.

### Cited Findings
- Microsoft's (now archived, still mirrored) "Create Journal Opening Balances" article: "Business Central includes several batch jobs that are provided to help in the transfer of legacy account balances to a newly configured company. You can easily transfer this data with the customer journal, the vendor journal, the item journal, or the G/L journal." First step is "to create a configuration package that includes the setup tables for those journals"; the G/L journal lines are created from the configuration worksheet (empty lines), exported to Excel, filled with posting/balancing accounts from legacy data, re-imported and posted; "the same apply to creating journal lines for customers, vendors, and items" — [Create Journal Opening Balances (To-Increase mirror of Microsoft doc)](https://business-central.to-increase.com/md/en-US/admin-how-to-create-journal-opening-balances); [LS Central mirror](https://help.lscentral150.lsretail.com/Content/Dynamics%20NAV/admin-how-to-create-journal-opening-balances.html). Note: this page no longer exists in the live docs repo `main` branch (file `admin-how-to-create-journal-opening-balances.md` is absent); mirrors are dated ~2021.
- Microsoft RapidStart "Tips and Tricks" page recommends migrating "G/L balances first, then open customer entries, then open item ledger entries" and splitting large data sets into smaller configuration packages — [Tips and Tricks: RapidStart Services (To-Increase mirror)](https://business-central.to-increase.com/md/en-US/admin-tips-and-tricks-rapidstart-services.md) (seen via search snippet only).
- The default configuration package "consists of 27 tables, including master data such as customers, vendors, items, and accounts" and explicitly includes **Gen. Journal Line**, **Item Journal Line**, Customer/Vendor/Inventory Posting Group tables; "you can work with the package to import and validate the data before you apply the package" — [Importing Business Data from Other Finance Systems](https://learn.microsoft.com/en-us/dynamics365/business-central/across-import-data-configuration-packages).
- MB-800 study guide (third-party, lower confidence): "General Ledger opening balances are posted via General Journals against a dedicated Migration Clearing / Suspense account (e.g., 99999)"; "Customer and Vendor opening balances must be migrated as detailed open invoices to preserve historical aging, document numbers, and future cash receipt/payment application"; "subledger journal entries automatically post to G/L control accounts (AR/AP) via posting groups and must be balanced against the Migration Clearing account"; "The process requires migrating the General Ledger trial balance using a Migration Clearing / Suspense Account... because control accounts have Direct Posting set to No" — [open-exam-prep MB-800 1.3 Opening Balances & Data Migration Strategies](https://open-exam-prep.com/study-guides/mb-800/company-creation-migration/opening-balances-migration).
- Second MB-800 study guide (third-party): "setup comes before master data, and master data before transactions", i.e. posting groups must exist before opening entries post — [aguidetocloud MB-800 Data Migration](https://www.aguidetocloud.com/guided/mb-800/domain-1/data-migration/).
- Bank is the explicit Microsoft-documented exception to "post TB directly": "Don't post the opening balance directly to the general ledger... Usually, you post the opening bank balance directly to the bank account, and the amount ends up in the G/L account. Alternatively, later you can reverse it out of the G/L account you use to balance the opening general ledger balance. In either case, you must balance any direct posting to the G/L account before you start your first bank reconciliation" — [Set Up Bank Accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/bank-how-setup-bank-accounts).
- Fixed assets are also sequenced explicitly by Microsoft: "First, ensure that general ledger integration isn't enabled for all depreciation books, then post the opening entries, and finally, turn on general ledger integration" — [Set Up General Fixed Assets Information](https://learn.microsoft.com/en-us/dynamics365/business-central/fa-how-setup-general).
- Inventory positive adjustments post to **Inventory Posting Setup → Inventory Account** with balancing **General Posting Setup → Inventory Adjmt. Account** ("Positive Adjmt., Negative Adjmt., Transfer | Direct Cost | ... | Inventory | Inventory Adjmt.") — [Design Details: Accounts in the General Ledger](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-accounts-in-the-general-ledger).
- Vendor tool (ECOSIRE, marketing page, low confidence) describes the same pattern: "open balance migration through general journal and customer/vendor opening ledger entries so the trial balance ties out" and "opening journals are isolated so they can be cleanly reversed and re-posted" — [ECOSIRE BC migration](https://ecosire.com/apps/dynamics-365-business-central/bc-quickbooks-xero-migration).

### Inferences
- Recommended sequence (synthesised): (1) setup + posting groups + No. series + dimensions + currencies/rates; (2) master data (G/L accounts, customers, vendors, items/SKUs, bank accounts, FA cards/depreciation books); (3) G/L trial balance **excluding** the AR, AP, inventory, bank and FA control accounts, with the net of those excluded accounts parked on a "MIGRATION CLEARING" G/L account; (4) customer open documents (Account Type Customer, Bal. Account = clearing); (5) vendor open documents (Account Type Vendor, Bal. Account = clearing); (6) bank balances (Account Type Bank Account, Bal. Account = clearing); (7) item journal positive adjustments — the balancing side goes to the **Inventory Adjmt. Account**, so point that (via a dedicated Gen. Prod. Posting Group or temporary General Posting Setup) at the clearing account, or post a G/L journal moving the inventory adjustment account balance to clearing; (8) FA journal lines (acquisition cost + accumulated depreciation) with G/L integration off, then turn integration on — because FA entries posted with integration off create no G/L entries, the FA cost/accumulated depreciation G/L accounts must come from the TB step, not from the FA journal; (9) verify clearing account = 0.00; (10) run Adjust Cost – Item Entries and Post Inventory Cost to G/L (if not automatic) and verify Inventory – G/L Reconciliation.
- "Post TB to clearing then sub-ledger detail against clearing" is the safer of the two options in the question, because it keeps Direct Posting = No on the control accounts and leaves a single account whose zero balance proves completeness. Posting the TB with control accounts included and then posting sub-ledger detail without a balancing line is not possible in BC (journals must balance), so double counting arises when someone posts the TB including control accounts **and** balances the sub-ledger lines to the same control account via a temporarily enabled Direct Posting.
- Inventory sits in a special position: the item journal creates value entries that only reach the G/L via Automatic Cost Posting or Post Inventory Cost to G/L (Question 6). If the TB load already includes the inventory G/L account and the item journal later posts to it too, the inventory G/L account doubles. Exclude the inventory account from the TB and let the item journal populate it, or set the Inventory Adjmt. Account for the migration posting-group combination to the clearing account.

### Gaps
- I found no current learn.microsoft.com page that prescribes the clearing-account method; the clearing-account pattern comes from study guides and vendor material, consistent with each other but not Microsoft-authored.
- No partner blog (Stoneridge, Innovia, ArcherPoint, Encore, Western Computer, Velosio, Catapult) with an explicit opening-balance cutover article surfaced in search; the Encore GP-to-BC FAQ only says Encore supplies "Opening Balance templates for each subledger" (snippet only).

## Key Question 2 — Posting date, fiscal year, Allow Posting From/To, closing periods, Close Income Statement, dedicated batch

### Takeaway
Post opening balances on the day before go-live (last day of the prior period) in a dedicated journal batch/document-number range with an explicit MIGRATION source identification, lock the Allow Posting From/To window on **General Ledger Setup** (and per-user on **User Setup**, which overrides it) to that single date during the load, and do not run Close Income Statement on the migration year until the P&L opening balances are confirmed — the fiscal year must exist (and be closed) before Close Income Statement can run.

### Cited Findings
- Posting-date lock: "On the General Ledger Setup page, define the period by entering dates in the Allow Posting From and Allow Posting To fields." "These posting periods apply to the company and to all users. To allow for exceptions, you can define different posting periods for specific users on the User Setup page. These posting periods overrule the periods specified on the General Ledger Setup page." Priority of checks: "1. User Setup page 2. General Ledger Setup page 3. General Journal Template page (when the Journal Templ. Name Mandatory toggle is enabled on the General Posting Setup page)." Date-formula alternative exists (`Allow Posting From Date Formula`), evaluated against the user's work date, so "Use fixed dates when you need strict, administrator-controlled boundaries that users can't influence." (page dated 03/18/2026) — [Specify posting periods](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-specify-posting-periods).
- User Setup also carries time constraints: "Administrators can define periods of time during which specified users are able to post" — [Set up time constraints for users](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-define-granular-permissions#set-up-time-constraints-for-users).
- Adjust Cost – Item Entries is subject to the same date window: error "Posting date is not within your range of allowed posting dates" occurs when adjustment value entries fall outside User Setup / General Ledger Setup ranges; "Assigning a wider date range where you allow posting on the Inventory Period or General Ledger Setup pages lets you avoid the conflict" — [Error: Posting Date is not within your range of allowed posting dates](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-inventory-adjustment-value-entry-allowed-posting-dates).
- Closing the year: "You can't close a fiscal year before you create a new one." Closing sets **Closed** and **Date Locked** on all periods; "The fiscal year can't be opened again". "Although a fiscal year is closed, you can still post general ledger entries to it... the entries are marked as posted to a closed fiscal year and the Prior-Year Entry field is selected." — [Close accounting periods](https://learn.microsoft.com/en-us/dynamics365/business-central/year-close-account-periods).
- Close Income Statement: "The fiscal year must closed before the batch job can be run." It "creates entries that cancel out their respective balances... placed in a journal in which you must specify a balancing account and retained earnings account"; "You must post the journal yourself"; "The date on the lines that the batch job inserts in the journal is always a closing date for the fiscal year. The closing date is a fictitious date between the last day of the old fiscal year and the first day of the new year." "The Close Income Statement batch job can be used several times. You can post in a previous fiscal year, even after the income statement accounts have been closed, if you run the batch job again." — [Close income statement accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/year-close-income-statement).
- Inventory periods: "When you close an inventory period, no value changes can be posted in the closed period. This includes new value postings, expected or invoiced postings, changes to existing values, and cost adjustments." Pre-conditions to close: no negative inventory, all costs adjusted — [Design details: Inventory periods](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-inventory-periods).
- Posting-date choice (third-party): "most implementations use the day before go-live as the posting date for opening balances" and "Typically the last day of the previous period or the first day of the new period. This cleanly separates old-system and new-system transactions." — [aguidetocloud MB-800](https://www.aguidetocloud.com/guided/mb-800/domain-1/data-migration/); [open-exam-prep MB-800 1.3](https://open-exam-prep.com/study-guides/mb-800/company-creation-migration/opening-balances-migration).
- Journal batches are the unit of posting via API: "The journal resource type offers a bound action called `post` which posts the corresponding journal batch" — [journal resource type (API v2.0)](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_journal). A third-party connector guide warns "posting will commit all lines in that batch at once, so entries should be isolated" — [Apideck guide](https://developers.apideck.com/guides/journal-entries-expenses-mbc).
- Document balancing in journals: Posting normally requires lines to balance by posting date, document type and document number; the **Force Doc. Balance** setting on General Journal Templates (default true) controls this — [yzhums: Balance by document number and document type in the general journal](https://yzhums.com/41109/).
- Document numbering: "If the No. Series field on the journal batch is filled, then the posting function in general journals requires that the document number on individual or grouped journal lines be in sequential order"; the **Renumber Document Numbers** action fixes this and "respects related applications" — [Work with general journals](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-work-general-journals).

### Inferences
- Use the last day of the prior period (e.g., cutover 2026-06-30 for a 2026-07-01 go-live) so that opening entries do not appear in the first live period's net change, Aged AR/AP "as of" go-live equals legacy, and the first live period's Trial Balance net change shows only real activity. If the fiscal year is being closed at the same time (FY boundary go-live), mid-year P&L balances are not needed; otherwise load YTD P&L balances per account on the same cutover date.
- Avoid a closing date (C-date) for opening entries: Close Income Statement reserves closing dates and reports that filter "normal" dates would exclude them. (Inference from the closing-date behaviour cited above.)
- Lock pattern: set Allow Posting From = Allow Posting To = cutover date on General Ledger Setup during the load; give only the integration user a User Setup row with that window; after sign-off set the company window to go-live date onward so nobody can backdate into the migration date. Add a `Journal Templ. Name Mandatory` + dedicated template/batch (e.g., template GENERAL, batch "OB-MIG") so the batch filter is a reliable audit scope and so the Copy G/L Register to Journal reversal (Question 8) can target one register.
- Do not close the migration fiscal year or run Close Income Statement until the opening P&L (if any) is signed off; closing cannot be undone.

### Gaps
- No Microsoft page prescribes a posting date for opening balances; the "day before go-live" guidance is from study guides only.
- No source discussing whether to use a dedicated **Source Code** for migration; BC's standard source codes (GENJNL, ITEMJNL, FAJNL) will apply. Not verified whether a custom source code can be set on the journal template for filtering G/L Registers.

## Key Question 3 — VAT/tax on opening entries, unrealized VAT, VAT statement impact

### Takeaway
VAT is only calculated on a journal line when the G/L account/line carries a **Gen. Posting Type** (Sale/Purchase) together with VAT Bus./Prod. Posting Groups; keep these blank on migration lines so no VAT entries are created, and load the VAT control balances as plain G/L amounts so the first VAT statement/return after go-live is built from live transactions plus a manually reconciled opening VAT liability.

### Cited Findings
- The **Gen. Posting Type** field on the G/L Account Card (Posting FastTab) is set to "either Sale or Purchase" and then "Choose the VAT posting groups to use for the sales or purchase account" — i.e., VAT posting is driven by Gen. Posting Type + VAT groups on the account — [Set up VAT](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-setup-vat).
- Microsoft NAV finance training manual: Gen. Posting Type "Defines whether the account is used only for a Sale or Purchase transaction or with both types of transactions"; options blank, Purchase, Sale; it drives where VAT is posted — [80534 NAV2013 Finance Essentials (PDF, hosted by yzhums)](https://yzhums.com/wp-content/uploads/2023/12/80534_NAV2013_ENUS_FINESS_02.pdf).
- Error "Posting to Account must either be of type Purchase or Sale" occurs when posting groups are populated without a Gen. Posting Type or vice versa — [Dynamics Consultants finance FAQ](https://dynamics-consultants.co.uk/resources/business-central-training-centre/business-central-finance-faqs/) (snippet only).
- Same FAQ: "Any account which is a control account for a subledger, such as Customers, Vendors, VAT, Bank, Stock should only allow system posting" and manual postings to control accounts can be found by filtering G/L entries on "system-created entry = no" — [Dynamics Consultants finance FAQ](https://dynamics-consultants.co.uk/resources/business-central-training-centre/business-central-finance-faqs/).
- Unrealized VAT is enabled by the **Unrealized VAT** check box on **General Ledger Setup**, then per VAT Posting Setup line via **Unrealized VAT Type** (Blank / Percentage / First / Last / First (Fully Paid) / Last (Fully Paid)); "The VAT amount will be posted to this account [Sales VAT Unreal. Account], and stay there until the customer payment is posted. The amount is then transferred to the account for sales VAT." — [Set up unrealized VAT for cash-based accounting](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-setup-unrealized-vat).
- QuickBooks migration wizard note (shows that migrated open documents do need VAT setup if VAT is to be posted on them): "If you are using value added tax (VAT), you may need to add a business posting group and a product posting group to the posting setup so that you can post VAT amounts." — [QuickBooks Data Migration extension](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-extensions-quickbooks-data-migration).
- Microsoft docs on journals: "The VAT fields can be filled in on either the recurring journal line or on the allocation journal line but not on both" (confirms VAT fields are per journal line) — [Work with general journals](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-work-general-journals).

### Inferences
- Control: on every migration journal line, force `Gen. Posting Type` = blank, `Gen. Bus. Posting Group`/`Gen. Prod. Posting Group` = blank and `VAT Bus. Posting Group`/`VAT Prod. Posting Group` = blank (the API `taxCode` field maps to a tax/VAT group — leave it empty). Pre-flight check: query the G/L accounts used in the TB; any with Gen. Posting Type ≠ blank will default VAT groups onto the line when the account is entered, so either clear them on the line after insert or use the Posting Preview to confirm zero **VAT Entry** rows before posting.
- Customer/vendor open-document lines carry the gross (VAT-inclusive) remaining amount; VAT on those invoices was already reported in the legacy system, so no VAT entry is wanted. The opening output/input VAT liability balances go on the TB step as ordinary G/L balances on the VAT accounts (Direct Posting temporarily allowed on those accounts, or route through clearing).
- If AESL uses Unrealized VAT (cash-basis VAT), open invoices migrated without VAT entries will not move VAT from unrealized to realized when paid — the unrealized VAT balance for migrated invoices must be tracked outside BC until those invoices are settled, or migrated as real documents (sales/purchase invoices with VAT lines) rather than journal lines. This is an inference; no source addresses migrating open items under unrealized VAT.
- The first VAT Statement after go-live will show only VAT entries created post-cutover; the opening VAT G/L balance will not appear in the VAT Statement (which reads VAT Entries, not G/L balances) unless configured with G/L totaling lines. Inference from VAT statement design; not directly cited.

### Gaps
- No Microsoft page explicitly states "leave Gen. Posting Type blank to suppress VAT on opening balances"; this is derived from the setup pages and the training manual.
- No Bangladesh-specific VAT (Mushak-6.3 etc.) BC guidance exists in Microsoft docs; Bangladesh is a partner-led W1 country (see scope note). Any local VAT app from the implementing partner may add its own posting checks — unknown.

## Key Question 4 — Customer/vendor open items: one line per document, document type, multicurrency, posting groups, Direct Posting

### Takeaway
Load one general-journal line per open document (Account Type Customer/Vendor, Document Type Invoice or Credit Memo, original Document No., document/posting date, due date/payment terms) against the clearing account; for FCY items post in the document currency at the historical rate so the Adjust Exchange Rates batch job can revalue them later; keep Direct Posting = No on the AR/AP control accounts throughout.

### Cited Findings
- Lump-sum loading loses aging: lump sums "break aging and payment matching"; one line per invoice "gives accurate aging from day one"; a lump-sum "erases historical invoice numbers, obscures original document dates, distorts aging buckets" — [aguidetocloud MB-800](https://www.aguidetocloud.com/guided/mb-800/domain-1/data-migration/); [open-exam-prep MB-800 1.3](https://open-exam-prep.com/study-guides/mb-800/company-creation-migration/opening-balances-migration).
- Microsoft's QuickBooks wizard warns about partially paid documents: "We migrate only full amounts on sales and purchase documents. We do not update partially paid amounts... If you have received partial payments, you must update these manually... We recommend that you apply outstanding transactions before you migrate" — [QuickBooks Data Migration](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-extensions-quickbooks-data-migration).
- GP cloud migration brings AR/AP in as remaining amounts: "outstanding transactions are brought in with the amount remaining in Dynamics GP" — [Dynamics GP data migrated to Business Central online](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/migrate-dynamics-gp) (snippet).
- Aged AR back-dating in BC Power BI reports is built from detailed customer ledger entries — supporting the need for document-level entries — [Aged receivables back dating](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-powerbi-aged-receivables-back-dating).
- Adjust Exchange Rates on customers/vendors: "the batch job uses the exchange rate that was valid on the posting date specified for the batch job to adjust the currency... posts the amounts to the general ledger account that is specified in the Unrealized Gains Acc. field or the Unrealized Losses Acc. field on the Currencies page. Balancing entries are automatically posted to the receivables/payables account"; "The batch job processes all open customer ledger entries and vendor ledger entries. If there's an exchange rate difference for an entry, the batch job creates a new detailed customer or vendor ledger entry." Preview is available: "choosing the Preview Posting action on the Exch. Rates Adjustment report (Report 596) request page." Currency Exchange Rates fields: Exchange Rate Amount, Relational Exch. Rate Amount, Adjustment Exch. Rate Amount, Relational Adjmt Exch. Rate Amt, Fix Exchange Rate Amount ("Specifies if the currency's exchange rate can be changed on invoices and journal lines") — [Update currency exchange rates](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-update-currencies).
- Bank FCY: "For bank accounts, the batch job adjusts the currency by using the exchange rate that's valid on the posting date... posts the amounts to the general ledger account that is specified in the Realized Gains Acc. field or the Realized Losses Acc. field" — same page.
- Reversing FCY-adjusted payments is supported ("Reverse a customer and vendor ledger entry with a realized gain or loss entry") — [Reverse journal postings](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-reverse-journal-posting).
- Direct Posting on control accounts: "setting Direct Posting = No on the underlying control accounts (e.g., Accounts Receivable, Accounts Payable, Inventory) keeps manual general journals from bypassing the subledgers" — [open-exam-prep MB-800 8.1 Specific Posting Groups](https://open-exam-prep.com/study-guides/mb-800/posting-groups-architecture/specific-posting-groups) (snippet).
- Pre-close verification: "you can use the Customer - Trial Balance report to verify that the balance for a customer posting group is equal to the balance on the corresponding general ledger account on a certain date" — [Prepare pre-closing reports](https://learn.microsoft.com/en-us/dynamics365/business-central/year-prepare-preclose-reports).
- The standard API v2.0 `journalLines` resource exposes only: `accountType` (G/L Account, Customer, Vendor, Bank Account, Fixed Asset, IC Partner, Employee), `accountNumber`, `postingDate`, `documentNumber`, `externalDocumentNumber`, `amount`, `description`, `comment`, `taxCode`, `balanceAccountType`, `balancingAccountNumber`, plus `dimensionSetLines` navigation — there is **no** `documentType`, `documentDate`, `dueDate`, `paymentTermsCode`, `currencyCode`, or posting-group field — [journalLine resource type (v2.0)](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_journalline).

### Inferences
- Minimum field set per open-item line (Gen. Journal Line table 81): Posting Date = cutover date; Document Type = Invoice (positive) / Credit Memo (negative — do not post a negative Invoice, because later application and Aged AR document-type grouping assume signs by type); Document No. = legacy invoice number (or a prefixed form if collisions with BC No. Series are possible); External Document No. = legacy number (for vendors this is the field Apply Entries matches on); Document Date = original invoice date; Due Date = legacy due date (BC derives Due Date from Payment Terms + Document Date on validate, so set Payment Terms Code first, then overwrite Due Date explicitly); Currency Code + Currency Factor for FCY; Bal. Account Type = G/L Account, Bal. Account No. = clearing; Gen. Posting Type and VAT groups blank. Aged AR/AP in BC ages by Due Date or Posting/Document Date per the report option, so Document Date must be the original, not the cutover date.
- Because the standard `journalLines` API lacks Document Type, Due Date, Document Date, Currency Code and Payment Terms, an API-driven load of open items needs either (a) a custom AL API page over table 81 exposing those fields, (b) configuration-package import of Gen. Journal Line (table 81) via RapidStart (which exposes all fields), or (c) posting real sales/purchase invoices through the `salesInvoices`/`purchaseInvoices` APIs with a single "Migration" G/L line (which would create VAT entries unless a zero-VAT group is used, and would hit sales No. Series). Option (a) or (b) is the normal partner approach; this is an inference from the field list.
- FCY: enter the Currency Code on the line and set the line's Currency Factor to the legacy historical rate (or load a Currency Exchange Rate row with Starting Date ≤ cutover and the historical rate, and `Fix Exchange Rate Amount` not restricting edits) so that Amount (LCY) equals the legacy LCY carrying value; then the first post-go-live Adjust Exchange Rates run produces the correct unrealized gain/loss against the Unrealized Gains/Losses accounts of the Currencies page. If LCY amounts are forced to match legacy by overriding Amount (LCY) directly, the LCY total of AR will tie but each entry's implied rate may differ from the stored Currency Exchange Rate — acceptable and common.
- Toggle Direct Posting on the AR/AP control accounts only if the chosen approach needs it (it should not with the clearing-account method). If it is toggled, record before/after values and re-check at sign-off with a G/L Entry filter "Source Code = GENJNL and G/L Account = control account" (equivalent to the "system-created entry = no" check cited above).

### Gaps
- No source quantifies how Aged Accounts Receivable (report 10040 NA / 120 W1 "Aged Accounts Receivable") treats a migrated invoice whose Document Date predates the Posting Date — the behaviour is standard (aging by chosen date field) but not cited here.
- No source found on the exact Gen. Journal Line fields (Currency Factor, Document Date) accepted by configuration packages for journal import; the RapidStart doc only lists the table.

## Key Question 5 — Dimensions on opening entries; Code Mandatory blocking posting

### Takeaway
Carry at least the reporting dimensions (Department/Region/Branch) on opening entries if post-go-live reports need them, but be aware that default dimension rules (Code Mandatory / Same Code) on accounts, customers, vendors or items are enforced at posting time and will block imported journal lines that lack the value; Microsoft explicitly warns not to use Code Mandatory/Same Code on accounts used by Adjust Exchange Rates or Post Inventory Cost to G/L.

### Cited Findings
- "If you want to require a dimension but don't want to assign a default value to the dimension, leave the Dimension Value Code field blank, then select Code Mandatory in the Value Posting field." Warning: "If an account is used in an Adjust Exchange Rates or Post Inventory Cost to G/L batch job, don't select Code Mandatory or Same Code. These batch jobs can't use dimension codes." Journal lines can carry dimensions via shortcut dimension fields and the Dimensions action — [Work with dimensions](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-dimensions).
- Adjust Exchange Rates has a **Dimension Posting** option (Source Entry Dimensions / No Dimensions / G/L Account Dimensions) and "assigns the dimensions from the customer or vendor ledger entries to the adjustment entries, and posts adjustments for each combination of dimension values" — [Update currency exchange rates](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-update-currencies).

## Key Question 6 — Inventory: item journal positive adjustments, cost posting flags, cost adjustment, G/L tie-out

### Takeaway
Load stock as Item Journal lines with Entry Type **Positive Adjmt.**, a Unit Cost per line (per location/variant/lot/serial, with expiration dates via item tracking on lines), then run **Adjust Cost – Item Entries** and, unless **Automatic Cost Posting** is on, **Post Inventory Cost to G/L**; tie the **Inventory Valuation** report to the inventory G/L account using the **Inventory – G/L Reconciliation** page, and keep the inventory G/L account out of the TB load to avoid double counting.

### Cited Findings

- Automatic Cost Adjustment field on Inventory Setup (Never/Day/Week/Month/Quarter/Year/Always); "it is recommend that you run the Adjust Cost - Item Entries batch job as often as possible, during nonworking hours" — [Design details: Cost adjustment](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-cost-adjustment).

### Inferences
- Double-counting control: the only two legitimate sources of the inventory G/L balance are (a) value entries posted via Automatic Cost Posting / Post Inventory Cost to G/L, or (b) a direct G/L line. Choose (a): exclude the inventory G/L account from the TB journal, park the equivalent amount on the clearing account, and let the Item Journal's Inventory Adjmt. Account credit be mapped (for the migration Gen. Bus./Gen. Prod. combination) to the clearing account so it nets out. If AESL's partner prefers (b), then Automatic Cost Posting must be OFF during the item journal load, and Post Inventory Cost to G/L must **not** be run for the migration value entries — which is fragile because the batch job will pick them up later unless Cost Posted to G/L is managed; hence (a) is preferred.
- For a distributor with many SKUs/locations, generate one item journal line per Item + Variant + Location + (Lot/Serial), Unit Cost = legacy unit cost (for Average/FIFO items the opening layer's cost becomes the first inbound layer; for Standard-cost items the line's unit cost is forced to the standard and any difference goes to variance). Quantity × Unit Cost totals per inventory posting group must equal the legacy inventory valuation per group/location.
- Date controls: ensure User Setup / General Ledger Setup / Inventory Periods allow the cutover date for both the item journal and later Adjust Cost runs; closing an Inventory Period for the cutover date after sign-off prevents backdated value changes.

## Key Question 7 — Fixed assets: acquisition + accumulated depreciation, depreciation books, G/L integration

### Takeaway
Microsoft's documented procedure is: turn off every Integration toggle on each Depreciation Book Card, post per asset in the **FA journal** (not FA G/L journal) an acquisition-cost line, a line with accumulated depreciation to the end of the prior fiscal year, and a line with current-year depreciation up to the date BC starts depreciating, then turn integration back on; the FA G/L balances come from the TB load.

### Cited Findings
- "Enable general ledger integration by following the next steps. First, ensure that general ledger integration isn't enabled for all depreciation books, then post the opening entries, and finally, turn on general ledger integration." Steps: open **Depreciation Books** → **Depreciation Book Card** → "On the Integration FastTab, turn off all of the toggles. If you have more than one depreciation book, repeat this step for each one." "In the fixed asset journal, enter the following lines for each asset: A line with the acquisition cost. A line with the accumulated depreciation to the end of the previous fiscal year. A line with the accumulated depreciation from the start of the current fiscal year to the date that Business Central is set to start calculating the depreciation. If you have other opening balances you can also enter them now, such as write-down and appreciation. After you enter and post the journal lines for each asset, turn on general ledger integration in the depreciation books. - "You must assign a fixed asset posting group to each fixed asset that has a depreciation book with the G/L integration option enabled"; FA posting groups define the G/L accounts for acquisition cost, accumulated depreciation, disposals — [Introduction to setting up a fixed asset posting group](https://learn.microsoft.com/en-us/training/modules/posting-groups-setup/1-introduction-setup).

### Inferences
- Because FA journal postings made with integration off create FA ledger entries but no G/L entries, the FA cost and accumulated depreciation G/L accounts must be included in the G/L TB load (unlike AR/AP/bank/inventory). Sign-off tie-out: FA ledger (Fixed Asset – Book Value report, per FA posting group) vs. G/L account balances.
- The "FA Posting Date" and "Posting Date" on FA journal lines should both be ≤ cutover; set Depreciation Starting Date and "Last Depreciation Date" consistent with the current-year line so the first BC depreciation run (Calculate Depreciation) starts from go-live, not from the acquisition date.
- Make the Integration toggles change part of a checklist with before/after screenshots; forgetting to turn them back on means post-go-live acquisitions/depreciation silently bypass the G/L.

## Key Question 8 — Bank: opening balance per bank account, reconciliation statement, outstanding checks

### Takeaway
Post the opening bank balance as a bank account ledger entry (general journal line with Account Type Bank Account, or via a bank reconciliation), never directly to the bank's G/L account; load uncleared checks/deposits as individual bank ledger entries dated at cutover so that the first **Bank Acc. Reconciliation** (with Statement Date = cutover and Statement Ending Balance = bank statement) leaves them as outstanding.

### Cited Findings
- "To fill in the Balance field with an opening balance, you must post a bank account ledger entry with the amount in question. You post the entry through a bank account reconciliation." "Alternatively, you can implement the opening balance as part of general data creation in new companies using the Migrate Business Data assisted setup guide." IMPORTANT: "Don't post the opening balance directly to the general ledger. Entries in the G/L account that were posted directly to it typically prevent you from reconciling the bank account. With foreign currency bank accounts, direct posting results in differences that accumulate as you post more bank reconciliations... you must balance any direct posting to the G/L account before you start your first bank reconciliation" — [Set Up Bank Accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/bank-how-setup-bank-accounts).
- Bank reconciliation mechanics: "After you enter a date in the Statement Date field, the Bank Acc. Reconciliation page filters the bank ledger entries to show only entries up to that date... with the difference being the outstanding payments and checks." You can post when Total Balance of statement lines = Balance To Reconcile + Balance Last Statement; "Balance Last Statement ... The value is zero if it's your first bank account reconciliation." Report fields: "G/L Account No. Balance at date — A discrepancy in this field and the previous ones might indicate that you posted directly to the G/L account... The Test Report shows a warning if you have direct postings"; "Outstanding Checks — The sum of unmatched bank ledger entries for checks that have a posting date on or before the statement ending date"; "Bank Account Balance — The sum of the values for the bank statement ending balance, outstanding bank transactions, and outstanding checks"; the **Bank Account Statement** report (Test Report action) "shows the same fields as at the header of the Bank Acc. Reconciliation page"; the Bank Statement report has an **Outstanding Entries** toggle to list outstanding entries — [Reconcile bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/bank-how-reconcile-bank-accounts-separately).
- Bank FCY revaluation uses Adjust Exchange Rates with Realized Gains/Losses accounts (see Q4) — [Update currency exchange rates](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-update-currencies).
- Pre-closing report for banks: "Bank Acc. - Detail Trial Bal." — [Prepare pre-closing reports](https://learn.microsoft.com/en-us/dynamics365/business-central/year-prepare-preclose-reports).
- Partner how-to (HBP Group, UK) describes entering the bank opening balance through a General Journal with the counter-entry to the linked G/L account — [HBP Group: add an opening balance to a bank account](https://thehbpgroup.co.uk/blog/how-to-add-an-opening-balance-to-a-bank-account) (snippet; third-party).

### Inferences
- For each bank account: (1) one general journal line, Account Type = Bank Account, Amount = legacy **book** balance (bank statement balance − outstanding checks + deposits in transit), Bal. Account = clearing; or (2) book-balance split as: statement balance line + one line per uncleared check/deposit (Document Type Payment, Document No. = check no.), which is what makes the first reconciliation clean. Then run Bank Acc. Reconciliation with Statement Date = cutover and Statement Ending Balance = bank statement balance; the uncleared items remain outstanding. Option (2) is the inference supported by the "Outstanding Checks" definition above.
- Do not let the bank's G/L account appear in the TB journal (it must be populated solely by bank-ledger-driven entries via the Bank Account Posting Group), matching the Microsoft IMPORTANT note.

### Gaps
- No Microsoft page describes loading outstanding checks specifically as opening data; derived from the reconciliation field definitions.

Balance on the template requires balance per Document No./Type/Date — [Work with general journals](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-work-general-journals); [yzhums 41109](https://yzhums.com/41109/).
- RapidStart alternative for bulk: configuration packages can be validated before apply and "Splitting large data sets into smaller configuration packages makes long imports easier to manage" — [Importing Business Data](https://learn.microsoft.com/en-us/dynamics365/business-central/across-import-data-configuration-packages); [RapidStart tips (mirror)](https://business-central.to-increase.com/md/en-US/admin-tips-and-tricks-rapidstart-services.md).
- Idempotency pattern references (general, not BC-specific): generate one key per logical operation, reuse on retries, make the key claim atomic (unique constraint) — [IETF draft Idempotency-Key header](https://greenbytes.de/tech/specs/draft-ietf-httpapi-idempotency-key-header-01.html); [Merge: idempotency for accounting POSTs](https://help.merge.dev/articles/3428903208-idempotency).

### Inferences
- Idempotency design for BC: make `documentNumber` (and `externalDocumentNumber`) deterministic per legacy record (e.g., `OB-AR-<legacy invoice no>`, `OB-GL-<account>-<seq>`), store the mapping in the loader's own state table, and before every insert (a) GET the journal's lines filtered by `documentNumber eq '...'` and (b) query posted ledger entries (`generalLedgerEntries`, `customerLedgerEntries`... or the `Document No.` on the G/L Entry) to skip already-posted keys. BC will not reject a duplicate document number on its own (document numbers are not unique in G/L Entry), so this must be enforced client-side. Clear the batch's **No. Series** so BC does not demand sequential numbering and so Renumber is never needed.
- Chunking: insert lines in `$batch` requests of ≤100 operations with `Isolation: snapshot` so a chunk either fully lands in the journal or not at all; keep a journal batch to a size the 8-minute operation timeout can post (the question's 500–1000 lines per batch is plausible; no Microsoft figure exists — see Gaps). Use one journal batch per logical group (e.g., OB-AR-01…NN, OB-AP-01…, OB-GL) so a failed post is isolated and re-postable; each batch balances to clearing by itself.
- Dry run: before `Microsoft.NAV.post`, run the journal's Test Report or Posting Preview in the UI (not exposed in the standard API), or post first in the production-copy sandbox with the identical payload and compare the sign-off pack. Respect rate limits with exponential back-off on 429/503 and honour Retry-After; keep concurrency ≤5 per user.
- Rollback: since each posting creates a G/L Register, record the register numbers returned per batch (query `G/L Registers`/`generalLedgerEntries` after post); rollback for G/L/AR/AP/bank = Copy G/L Register to Journal with opposite signs (or Reverse Transaction per entry); for inventory = negative adjustment item journal keyed to the same lines; for FA = reversing FA journal with integration off. Because Reverse Transaction works once per entry, never partially reverse and re-post the same register twice.
- Permissions: give the integration app a custom permission set limited to Gen. Journal Line/Item Journal Line/FA Journal Line (insert/modify/delete), the posting codeunits and read on ledger tables, plus the relevant setup tables read-only; keep D365 AUTOMATION only if its broader scope is acceptable; disable the Entra application card (State = Disabled) after cutover.
- Rehearse the entire load at least twice in a sandbox copied from production (same version, same PTEs/apps), delete and re-copy the sandbox between runs because there is no refresh.

### Gaps
- No Microsoft documentation defines an idempotency key or duplicate detection for journalLines; the statement that BC does not enforce uniqueness of Document No. is from product behaviour, not a citation.
- No source gives a recommended journal batch size (lines per post) for BC Online; only the $batch cap (100) and the 8-minute operation timeout are documented.
- The standard `journalLines` API cannot set Document Type/Due Date/Currency/Posting Groups (Q4); whether the standard `post` action triggers the journal's Test Report checks identically to the UI is not documented.

## Key Question 11 — Microsoft "Migrate business data" / data-migration wizards and their limitations

### Takeaway
The **Migrate Business Data** assisted setup imports master data (vendors, customers, items) from Excel or QuickBooks and, for QuickBooks, "Beginning Balance transactions in General Ledger", on-hand quantities and open customer/vendor documents as **unposted** transactions — it is not a general opening-balance engine, does not handle partial payments or open orders, and I found no evidence it posts via a batch named "MIGRATION" (claim unverified).

### Cited Findings
- Assisted Setup entry: "Migrate Business Data — Lets you import your existing company data such as vendors, customers, and items from Excel or Quickbooks." — [Getting ready for doing business](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-get-ready-business).
- Microsoft recommends wizards for GP/NAV/QuickBooks: "We recommend that you use data migration wizards to import data from Dynamics GP, Dynamics NAV, or QuickBooks." — [Importing Business Data from Other Finance Systems](https://learn.microsoft.com/en-us/dynamics365/business-central/across-import-data-configuration-packages).
- QuickBooks extension migrates: customers, vendors, items, Chart of Accounts, "Beginning Balance transactions in General Ledger", "On-hand Quantities for Inventory Items", "Open documents for customers and vendors, such as invoices, credit memos and payments". Limits: "We migrate only full amounts... We do not update partially paid amounts"; "We do not migrate purchase orders or sales orders"; "After you migrate data, transactions have the status Unposted, so you can review them... to review payment journals, go to the Payment Journals page"; "If you are using value added tax (VAT), you may need to add a business posting group and a product posting group"; "Verify the beginning balances for accounts in the general ledger. QuickBooks does not store the current balance for all accounts" — [QuickBooks Data Migration](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-extensions-quickbooks-data-migration); same for [QuickBooks Online](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-extensions-quickbooks-online-data-migration).
- The older Dynamics GP Data Migration extension is deprecated since 15.3 in favour of the Cloud Migration wizard — [Dynamics GP Data Migration Extension (deprecated)](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-extensions-dynamicsgp-data-migration).
- Community experience with the QuickBooks tool: exported more than the import handled, didn't export open orders, didn't map some fields such as payment terms, item numbers reassigned — [DynamicsUser: Migration from QuickBooks Enterprise](https://www.dynamicsuser.net/t/migration-from-quickbooks-enterprise-to-business-central/87584) (anecdotal).
- Bank page confirms the wizard can create a bank opening balance "as part of general data creation in new companies using the Migrate Business Data assisted setup guide" — [Set Up Bank Accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/bank-how-setup-bank-accounts).

### Inferences
- For AESL (legacy system presumably not QuickBooks/GP/NAV), the wizard's Excel path only covers master data; opening balances must go through journals (configuration package → Gen. Journal Line / Item Journal Line, or API/custom API), which is the Microsoft "Create Journal Opening Balances" approach cited in Q1.

### Gaps
- The claim that the migration tool posts via a General Journal Batch named "MIGRATION" could not be verified in any current Microsoft doc; the docs only say QuickBooks-migrated transactions land unposted on their normal pages (e.g., Payment Journals). Treat "MIGRATION" batch naming as unconfirmed (it may be a convention from specific partner tools or older GP migration code).
