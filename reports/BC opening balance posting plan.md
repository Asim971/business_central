# Post AGI Opening Balances Through Governed Journals

Opening balances for company **AGI** in environment **QA-AGI** should be loaded as General Journal lines and posted with Business Central's own posting codeunits, never by writing ledger tables, and the new `business_central scripts` repository can do this today for the **G/L trial balance and bank balances using the standard `journals`/`journalLines` API plus `Microsoft.NAV.post`**, but **not for customer and vendor open items**, because the standard `journalLines` page hard-codes `Document Type = " "` and exposes no Due Date, Document Date or Currency Code (verified in Microsoft's shipped AL source, not just docs). The customer/vendor sub-ledgers therefore need one small addition to the existing `AnwarLogistics` AL extension: a custom API page over `Gen. Journal Line` (`api/anwarGroup/logistics/v1.0/openingJournalLines`) that exposes those fields, after which the **standard `Microsoft.NAV.post` action posts the batch regardless of how its lines were created** (Microsoft's own API E2E test posts Customer/Invoice lines that way). The usedynamics.com "Customer Opening Entries" recipe (one journal line per open document, balanced against the receivables account) is consistent with Microsoft's own GP/QuickBooks migrators and the MB-800 lab, but we recommend the **migration-clearing-account variant** instead, because it keeps `Direct Posting = No` on control accounts and gives the scripts a single machine-checkable completeness invariant: *clearing account = 0.00*. The logistics-distribution repo contributes a proven S2S token pattern (`AzureAd__*` app registration, scope `https://api.businesscentral.dynamics.com/.default`), URL bases, governor limits, a durable write-command vocabulary (probe-before-apply, never retry a write in-process, timeout = unknown outcome) and AL conventions (`anwarGroup`/`logistics`/`v1.0`, ids 70100-70199, `ODataKeyFields = SystemId`), but it has **no journal endpoint, no finance write, and no ledger-entry read** today, and the existing extension version on QA-AGI is 1.25.0.0, so a new AL version must be published before AR/AP loads can run. The plan below gives a seven-phase cutover (prepare BC → publish AL → scaffold scripts → CSV templates → rehearse twice → cut over sub-ledgers then G/L → reconcile, lock down, keep rollback ready), with deterministic `Document No.` keys as idempotency identity, one journal batch per ≤200-line chunk, OData `$batch` of ≤100 operations with `Isolation: snapshot`, and a reconciliation pack that Finance signs before `Allow Posting From/To` is re-opened.

## 1. What the logistics-distribution repo already provides, and what must not be assumed

The backend is a .NET 10 modular monolith that is, by rule, the only BC caller; "BC writes must be coarse, idempotent, asynchronous and reconcilable. A timeout is an unknown outcome to reconcile, not permission to blindly retry a second side effect" ([AGENTS.md](/home/user/logistics-distribution/AGENTS.md)). That sentence is the design brief for the opening-balance scripts as well, even though they will live in a separate repository. The reusable assets fall into five groups.

**Token acquisition and URL bases.** Production code acquires app-only tokens through Microsoft.Identity.Web: `BcAppTokenSource` single-flights `IAuthorizationHeaderProvider.CreateAuthorizationHeaderForAppAsync` for scope `https://api.businesscentral.dynamics.com/.default` on the named `Entra` scheme, with a 20-second acquisition timeout, and `BcAuthorizationHandler` stamps the header outside the resilience handler so retries reuse it ([BcAppTokenSource.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcAppTokenSource.cs); [BcAuthorizationHandler.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcAuthorizationHandler.cs)). The registration binds the `AzureAd` section (`TenantId`, `ClientId`, `ClientSecret`) via `.AddMicrosoftIdentityWebApi(...).EnableTokenAcquisitionToCallDownstreamApi().AddInMemoryTokenCaches()` ([EntraRegistration.cs](/home/user/logistics-distribution/backend/src/Logistics.Api/Auth/EntraRegistration.cs)). For a script, the lighter precedent is `scripts/check-al-object-ids.sh`, which sources `backend/.env` and POSTs `grant_type=client_credentials` with `AzureAd__ClientId`/`AzureAd__ClientSecret` to `https://login.microsoftonline.com/${Bc__TenantId}/oauth2/v2.0/token`, then calls `/api/v2.0/companies` and the automation `extensions` list ([check-al-object-ids.sh](/home/user/logistics-distribution/scripts/check-al-object-ids.sh)). This matches Microsoft's BCTech S2S samples (`ConfidentialClientApplicationBuilder ... AcquireTokenForClient("https://api.businesscentral.dynamics.com/.default")`) ([BCTech AcquireToken-AsApplication.ps1](https://raw.githubusercontent.com/microsoft/BCTech/ccb6c3d36f72b784fb9757316f6f296f0a58ea71/samples/PSOAuthBCAccess/AcquireToken-AsApplication.ps1)). The URL bases are fixed strings worth copying verbatim: `StandardBase = /v2.0/{TenantId}/{Environment}/api/v2.0` and `CustomBase = /v2.0/{TenantId}/{Environment}/api/anwarGroup/logistics/v1.0` on `BaseUrl = https://api.businesscentral.dynamics.com` ([BcApiClient.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcApiClient.cs); [BcOptions.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcOptions.cs)).

**HTTP conventions and limits.** Every client stamps `Accept-Language: en-US`; bulk reads must carry explicit `$select` and `$top` because a `$select` naming a field the page lacks fails the whole request; sync reads add `Data-Access-Intent: ReadOnly` and follow `@odata.nextLink`; `If-Match` is only ever a captured ETag, never `*`; bound actions answer 200/201 with an empty body and a `Location` header, and `Prefer: return=representation` changes nothing ([BcLanguageHandler.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcLanguageHandler.cs); [BcApiClient.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcApiClient.cs); [BcIfMatch.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcIfMatch.cs)). The resilience policy is explicit that **"A BC WRITE IS NEVER RETRIED IN THIS PROCESS"**: `Retry.ShouldHandle` returns false for POST/PATCH/PUT/DELETE and for background work, and the governor keeps in-flight calls strictly below five per S2S principal (`MaxInFlight 4`, `ReservedInteractiveSlots 1`, `SustainedRatePerSecond 14`, `BurstCapacity 40`) ([BcServiceCollectionExtensions.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcServiceCollectionExtensions.cs); [appsettings.json](/home/user/logistics-distribution/backend/src/Logistics.Api/appsettings.json)). Those numbers matter for the scripts because BC applies its per-user limits (5 concurrent, 6,000 requests per 5-minute window) to service principals exactly as to humans ([Operational limits](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/operational-limits-online)); a loader that reuses the same Entra app shares the backend's budget.

**Durable write-command vocabulary.** The write spine is a Postgres job queue plus a `bc_write_commands` ledger with outcomes Unobserved/Landed/NotLanded/Undecided/Abandoned, a unique business key, and the contract that `ProbeAsync` is "A GET, never a write", that neither probe nor apply "may decide a retry, a backoff or a dead-letter", and that a handler probes BC before every re-attempt ([IBcWriteCommand.cs](/home/user/logistics-distribution/backend/src/Logistics.Core/Bc/IBcWriteCommand.cs); [BcWriteCommandRecord.cs](/home/user/logistics-distribution/backend/src/Logistics.Core/Bc/BcWriteCommandRecord.cs); [BcWriteCommandJobHandler.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Jobs/Handlers/BcWriteCommandJobHandler.cs)). The scripts should not import this code (it depends on Postgres and the host), but they should reproduce its state machine in a file-backed run ledger, as Section 4.10 specifies.

**AL extension conventions.** `app.json` declares `AnwarLogistics`, publisher `Anwar Group`, version `1.26.3.0`, platform/application `28.0.0.0`, runtime `17.0`, `idRanges 70100-70199`, `NoImplicitWith`; every API object uses `APIPublisher='anwarGroup'`, `APIGroup='logistics'`, `APIVersion='v1.0'`, `ODataKeyFields = SystemId`, camelCase field names and `Rec.ReadIsolation := IsolationLevel::ReadCommitted` in `OnOpenPage`; posting actions must be idempotent by correlation id; "Never assume an object is deployed because it exists in source" ([app.json](/home/user/logistics-distribution/bc-extension/app.json); [bc-extension/AGENTS.md](/home/user/logistics-distribution/bc-extension/AGENTS.md); [PingsApi.Page.al](/home/user/logistics-distribution/bc-extension/src/PingsApi.Page.al)). Pages 70100-70113, tables 70100-70105, codeunits 70101-70103 and 70109-70120, queries 70110-70112, enums 70100-70101 and permission sets 70102-70103 are taken, and `scripts/check-al-object-ids.sh` must be run before any publish because a third-party "Commercial Operations" app once declared overlapping ids 70100-70349 ([check-al-object-ids.sh](/home/user/logistics-distribution/scripts/check-al-object-ids.sh)). The permission set already grants `codeunit "Gen. Jnl.-Check Line" = X` for posting-date validation ([LogisticsPermissions.PermissionSet.al](/home/user/logistics-distribution/bc-extension/src/LogisticsPermissions.PermissionSet.al)), and the version gate reads the extension version from the live module via `pings` ([BcExtensionVersionGate.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcExtensionVersionGate.cs)).

**Testing conventions.** Three gated fact types (`[Fact]`, `[DbFact]` on a real Postgres, `[BcFact]` only when `BC_INTEGRATION_TESTS=1`), a frozen write-route register that may only shrink, idempotency proven by "counted persisted side effects" rather than status codes, and the standing rule that "a BC task is not complete until it has run against real Dev-AGI. The emulator is evidence about wiring, never about Business Central" ([backend/AGENTS.md](/home/user/logistics-distribution/backend/AGENTS.md); [bc-write-routes.frozen.txt](/home/user/logistics-distribution/backend/tests/Logistics.Tests/TestSupport/BcEmulator/bc-write-routes.frozen.txt); [runbook-bc-extension.md](/home/user/logistics-distribution/docs/runbook-bc-extension.md)). Runbooks carry a "controlled-live" table whose rows stay `PENDING — approval required` until a dated run exists ([runbook-bc-durable-posting.md](/home/user/logistics-distribution/docs/runbook-bc-durable-posting.md)).

What must **not** be assumed is just as important. A repo-wide grep for `journal|opening balance|customer ledger|aged receivable` finds no implementation: no standard `journals`, `journalLines`, `customerPayments`, `generalLedgerEntries` or ledger-entry call exists, the platform mirrors customer `balance`/`overdueAmount` read-only through `$expand=customerFinancialDetail`, and the PRD explicitly says "Not an accounting system. No ledger, no invoice numbering, no tax computation. The platform *requests* postings; BC *performs* them" ([MirrorEntities.cs](/home/user/logistics-distribution/backend/src/Logistics.Core/Sync/MirrorEntities.cs); [LogisticsDistributionPRDv1_2.md](/home/user/logistics-distribution/docs/LogisticsDistributionPRDv1_2.md)). The extension has no finance object; `Bc:CompanyId` is used only by the ping and startup validation, every other call takes a per-call company GUID resolved from `bc_companies` ([BcApiClient.cs](/home/user/logistics-distribution/backend/src/Logistics.Infrastructure/Bc/BcApiClient.cs)); `appsettings.json` defaults `Bc:Environment` to `Dev-AGI`, while the October runbook says 1.25.0.0 is what is published to **QA-AGI** and "AL 1.26.0.0 is NOT published" ([appsettings.json](/home/user/logistics-distribution/backend/src/Logistics.Api/appsettings.json); [runbook-bc-extension.md](/home/user/logistics-distribution/docs/runbook-bc-extension.md)). No GitHub Actions secret for `AzureAd__ClientSecret` or `Bc__*` exists (only `RAILWAY_TOKEN_DEV`/`RAILWAY_TOKEN_QA`), and CI "has been refused at start for GitHub Actions billing since 2026-09-12" ([.github/workflows/ci.yml](/home/user/logistics-distribution/.github/workflows/ci.yml); [known-failures.txt](/home/user/logistics-distribution/backend/tests/known-failures.txt)). Finally, QA-AGI also runs a third-party `DynamicERP` app (objects 50100-50249) that fires a webhook and commits from inside a warehouse-shipment insert ([dynamicerp-owner-guideline-2026-10-05.md](/home/user/logistics-distribution/docs/dynamicerp-owner-guideline-2026-10-05.md)); nothing suggests it subscribes to journal posting, but the rehearsal must prove that.

## 2. How Business Central expects opening balances to be posted: Microsoft's guidance versus the usedynamics recipe

Microsoft's current end-user documentation has no page literally titled "Set up opening balances"; the old "Create Journal Opening Balances" article survives only on partner mirrors, and its content was folded into the dev-itpro page on configuration packages, which describes running **Create G/L Acct. Journal Lines**, exporting the journal to Excel, entering posting and balancing accounts from legacy data, re-importing, and posting from the configuration worksheet, and states that "The G/L account steps also apply to customer, vendor, and item journals" ([Apply company configuration packages](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/apply-company-configuration-packages)). The mechanism behind every variant is the posting group: "Entries are created even when, for example, you post a journal line to a customer account, because an entry is posted to a general ledger receivables account through a posting group" ([Post transactions directly to the general ledger](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-post-transactions-directly)). Three Microsoft rules shape the sequence. Bank: "Don't post the opening balance directly to the general ledger ... you must balance any direct posting to the G/L account before you start your first bank reconciliation" ([Set up bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/bank-how-setup-bank-accounts)). Fixed assets: "ensure that general ledger integration isn't enabled for all depreciation books, then post the opening entries, and finally, turn on general ledger integration", with one acquisition-cost line and accumulated-depreciation lines per asset in the FA journal ([Set up fixed assets](https://learn.microsoft.com/en-us/dynamics365/business-central/fa-how-setup-general)). Control accounts should refuse direct posting; Microsoft states this for bank posting groups ("We recommend that these G/L accounts have the **Direct Posting** field set to *No*") ([Set up posting groups](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-posting-groups)), and the posting codeunit enforces `GLAcc.TestField("Direct Posting", true)` for any non-system-created entry ([GenJnlPostLine.Codeunit.al](https://github.com/microsoft/BCApps/blob/main/src/Layers/W1/BaseApp/Finance/GeneralLedger/Posting/GenJnlPostLine.Codeunit.al)).

The most authoritative statement of *how Microsoft itself loads customer and vendor open items* is not a doc page but the shipped migration code. The Dynamics GP migrator creates, per open document, `CreateGeneralJournalLine(batch, DOCNUMBR, name, DOCDATE, 0D, amount, amount, '', ReceivablesAccountNo)` followed by `SetGeneralJournalLineDocumentType(TransType)` with payments and credit memos negated, that is, **Account Type Customer, Document Type Invoice/Payment/Credit Memo, Bal. Account = the receivables control account** ([GPCustomerMigrator.codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Apps/W1/HybridGP/app/src/Migration/Customers/GPCustomerMigrator.codeunit.al#L77-L180)); the QuickBooks migrator does the same with an explicit due date and `SetGeneralJournalLineExternalDocumentNo` ([MigrationQBCustomerMigrator.Codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Apps/W1/QBMigration/app/src/Customers/MigrationQBCustomerMigrator.Codeunit.al#L50-L110)); and the Data Migration Facade Helper fixes the field validation order (Account Type → Document No. → Account No. → Document Date → Posting Date → Due Date → Amount → Amount (LCY) → Currency Code → Bal. Account → blank Bal. posting groups) ([DataMigrationFacadeHelper.Codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Layers/W1/BaseApp/System/DataMigration/DataMigrationFacadeHelper.Codeunit.al#L262-L304)). Microsoft's MB-800 lab builds an **OPENING** template (Force Doc. Balance cleared, Copy Tax/VAT Setup to Jnl. cleared) with batches BALANCE, BANK, CUST (Bal. Account 10400 receivables) and VEND (Bal. Account 20100 payables) ([MB-800 Lab 09](https://microsoftlearning.github.io/MB-800-Business-Central-Functional-Consultant/Instructions/Labs/Lab09_Set_up_General_Journals.html)).

### Critical analysis of the usedynamics "Customer Opening Entries" article

The article (readable in this research only through search snippets; see Section 7) recommends "a dedicated general journal batch, with the customer on one line and the receivables account as the balancing account. Set the document type to Invoice for normal entries and Credit Memo for credit entries, and enter the original posted document number", so that posting "nets the general ledger to zero while still creating open customer ledger entries you can apply payments against later" ([usedynamics: Customer Opening Entries](https://usedynamics.com/business-central/details/customer-opening-entries/)). Its sibling pages sequence sub-ledgers (bank, customers, vendors, VAT, inventory) before a final zero-total G/L journal and recommend rehearsing in a copied company ([usedynamics: Opening Balances Strategy](https://usedynamics.com/business-central/details/opening-balances-strategy/); [usedynamics: Complete Opening](https://usedynamics.com/business-central/details/complete-opening/)).

Where it agrees with Microsoft: one line per open document with the original document number and Invoice/Credit Memo document types is exactly what the GP and QuickBooks migrators do, and balancing against the control account itself is the MB-800 lab pattern. Partner study guides add the reason: lump sums "break aging and payment matching" and one line per invoice "gives accurate aging from day one" ([aguidetocloud MB-800](https://www.aguidetocloud.com/guided/mb-800/domain-1/data-migration/)). The article's claim that the receivables account "is found through the customer posting group" is confirmed by the table code, which copies `Posting Group := Cust."Customer Posting Group"` when the account number is validated ([GenJournalLine.Table.al](https://github.com/microsoft/BCApps/blob/main/src/Layers/W1/BaseApp/Finance/GeneralLedger/Journal/GenJournalLine.Table.al)).

Where it is incomplete or where we depart from it. First, balancing against the receivables control account itself (call it **Technique A**) requires that account to accept direct postings for the duration of the load, because the Bal. Account side is a direct G/L entry, which contradicts the standing recommendation to keep `Direct Posting = No` on control accounts; a consultant who has used both methods notes that Technique A "can cause issues if a balance is reversed", whereas balancing to a suspense code and then reversing it into the AR G/L code mitigates "the risk of imbalance" ([thedynamicsexplorer, May 2024](https://thedynamicsexplorer.com/2024/05/09/dynamics-365-business-central-a-couple-of-methods-i-use-when-posting-opening-balances-for-sales-and-purchase-ledger/)). The MB-800 study guides teach the same **Technique B**: "subledger journal entries automatically post to G/L control accounts (AR/AP) via posting groups and must be balanced against the Migration Clearing account", precisely "because control accounts have Direct Posting set to No" ([open-exam-prep MB-800 1.3](https://open-exam-prep.com/study-guides/mb-800/company-creation-migration/opening-balances-migration)). Second, the snippets never mention Due Date or Document Date, yet these decide whether the first Aged Accounts Receivable in BC matches the legacy aged list: the aged reports age "from the due date, posting date, or document date" ([Prepare to close statements](https://learn.microsoft.com/en-us/dynamics365/business-central/year-prepare-close-statement)), and the table only computes a due date from payment terms when `Document Type = Invoice`, otherwise `"Due Date" := "Document Date"` ([GenJournalLine.Table.al](https://github.com/microsoft/BCApps/blob/main/src/Layers/W1/BaseApp/Finance/GeneralLedger/Journal/GenJournalLine.Table.al)). Third, the article says nothing about VAT suppression, which the MB-800 lab handles by clearing Copy VAT Setup, nor about `Allow Posting From/To`, nor about automation; it is a UI recipe. Fourth, the article is roughly six years old per the search summary; nothing in it is wrong for BC 2025-26, but it predates the per-user API limits and the current `journalLines` page behaviour. Our verdict: adopt its per-document structure and document-type discipline, replace its balancing account with a dedicated clearing account, add Document Date/Due Date/Currency per line, and keep Gen. Posting Type and VAT groups blank.

### Posting date, number series and VAT controls that the recipe leaves implicit

Opening entries should carry one posting date, the last day of the period before go-live, so that the first live period's net change shows only real activity; "most implementations use the day before go-live" is a study-guide convention, not a Microsoft rule ([open-exam-prep MB-800 1.3](https://open-exam-prep.com/study-guides/mb-800/company-creation-migration/opening-balances-migration)). Document Date must stay the legacy invoice date and Due Date the legacy due date. The date window is controlled by **General Ledger Setup → Allow Posting From/To**, overridden per user on **User Setup**, with the journal template as a third tier when `Journal Templ. Name Mandatory` is on ([Specify posting periods](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-specify-posting-periods)). The migration batches must have a blank **No. Series**, because a filled series "requires that the document number on individual or grouped journal lines be in sequential order" ([Work with general journals](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-work-general-journals)) and, more dangerously, a filled **Posting No. Series** makes codeunit 13 *replace* the line's Document No. at post time (`NoSeriesBatch.GetNextNo("Posting No. Series", ...)`), which would destroy the idempotency key ([GenJnlPostBatch.Codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Layers/W1/BaseApp/Finance/GeneralLedger/Posting/GenJnlPostBatch.Codeunit.al#L853-L872)). VAT is only calculated when a line carries a Gen. Posting Type with VAT groups ([Set up VAT](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-setup-vat)); with `Copy VAT Setup to Jnl. Lines` off on the batch, the API's `SetJournalLineValues` never copies posting groups to the line ([GraphMgtJournalLines.Codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Layers/W1/BaseApp/Integration/Graph/GraphMgtJournalLines.Codeunit.al#L52-L84)). Bangladesh is a partner-led W1 localization with no Microsoft VAT app ([Country/regional availability](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/compliance/apptest-countries-and-translations)), so opening VAT liabilities go in as plain G/L balances and the first Mushak return is built from live transactions plus a manually reconciled opening figure.

## 3. The standard journal API can post customer lines but cannot describe them

The decisive findings come from the AL source of Microsoft's `_Exclude_APIV2_` app rather than from documentation. Page 30049 "APIV2 - JournalLines" sets `Rec."Document Type" := " "` in `OnNewRecord`, filters `Document Type = " "` and `Account Type` in the range `G/L Account..Bank Account` in `OnOpenPage`, and resolves `accountId`/`accountNumber` only for G/L and Bank accounts ([APIV2JournalLines.Page.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Apps/W1/APIV2/app/src/pages/APIV2JournalLines.Page.al#L253-L265)); the helper that writes the posted JSON into the record always runs `Validate("Document Type", "Document Type"::" ")` ([GraphMgtJournalLines.Codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Layers/W1/BaseApp/Integration/Graph/GraphMgtJournalLines.Codeunit.al#L52-L84)). The exposed properties are `accountType`, `accountId`, `accountNumber`, `postingDate`, `documentNumber`, `externalDocumentNumber`, `amount`, `description`, `comment`, `taxCode`, `balanceAccountType`, `balancingAccountId`, `balancingAccountNumber`, plus `dimensionSetLines` ([journalLine resource](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_journalline)). Because the enum ordinals are G/L Account = 0, Customer = 1, Vendor = 2, Bank Account = 3 ([GenJournalAccountType.Enum.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Layers/W1/BaseApp/Finance/GeneralLedger/Journal/GenJournalAccountType.Enum.al)), a customer line created through this page is technically accepted, but it posts as a blank-document-type entry whose due date equals the posting date and whose currency is whatever the customer card dictates. That is an opening balance that will age wrong, apply wrong, and cannot be targeted by `customerPayments.appliesToInvoiceId`, which resolves only posted Sales Invoice Headers ([APIV2CustomerPayments.Page.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Apps/W1/APIV2/app/src/pages/APIV2CustomerPayments.Page.al)). The `customerPayments`/`vendorPayments` entities are not an alternative either: they hard-code `Document Type = Payment` and `Applies-to Doc. Type = Invoice` on the Cash Receipt/Payment templates ([GraphMgtJournalLines.Codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Layers/W1/BaseApp/Integration/Graph/GraphMgtJournalLines.Codeunit.al#L86-L114)).

Jnl.-Post", GenJournalLine)`, returning 204 ([APIV2Journals.Page.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Apps/W1/APIV2/app/src/pages/APIV2Journals.Page.al#L100-L122)), and Microsoft's own E2E test creates two `Document Type::Invoice`, `Account Type::Customer` lines in AL, calls `journals({id})/Microsoft.NAV.post`, asserts 204 with an empty body and asserts `Cust. So a custom AL page can fill the batch with fully described customer/vendor lines and the standard action posts them, which keeps the custom AL surface minimal. Table 81 already holds every field needed: `12 Currency Code`, `23 Posting Group`, `24/25 Shortcut Dimension 1/2`, `35/36 Applies-to Doc. Two posting-path details must be designed around. Codeunit 231 asks "Do you want to post the journal lines?" through `ConfirmManagement.GetResponseOrDefault(Text001, true)`, which a web-service session answers with the default, but if **General Ledger Setup → Post with Job Queue** is on it only *schedules* the post and shows a message, so the API still returns 204 while nothing has posted yet ([GenJnlPost.Codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Layers/W1/BaseApp/Finance/GeneralLedger/Posting/GenJnlPost.Codeunit.al#L57-L125)). And codeunit 13 locks `Gen. Journal Line` and `G/L Entry`, checks every line, posts, deletes the lines and commits, so after a successful post `GET journals({id})/journalLines` returns nothing and the only evidence is the ledger ([GenJnlPostBatch.Codeunit.al](https://github.com/microsoft/BCApps/blob/9f954e85cbed82e2c18b77d8513c22a7d2b2e035/src/Layers/W1/BaseApp/Finance/GeneralLedger/Posting/GenJnlPostBatch.Codeunit.al#L190-L345)). Verification therefore needs `generalLedgerEntries` (GET-only, exposes `documentNumber`, `accountNumber`, `debitAmount`, `creditAmount`) for G/L ([generalLedgerEntry resource](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_generalledgerentry)) and, because **v2.0 has no `customerLedgerEntries` or `vendorLedgerEntries` resource** ([v2.0 resources folder](https://github.com/MicrosoftDocs/dynamics365smb-devitpro-pb/tree/main/dev-itpro/api-reference/v2.0/resources)), two small read-only AL API pages over tables 21 and 25.

The platform limits bound the batching design: 100 operations per `$batch`, 5 concurrent requests, 6,000 requests per 5-minute window, 8-minute operation timeout (408), 10-minute request limit (504), 429 on breach ([Operational limits](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/operational-limits-online); [Working with API limits](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/dynamics-rate-limits)). A `$batch` with `Isolation: snapshot` runs in one session and, unless AL commits, one transaction: "if an inner request fails after another request(s) has committed changes, all changes within a batch will be reverted" ([Using OData transactional $batch requests](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/use-odata-batch)). Known issue KA-24233 (snippet-only) reports duplicate `Line No.` assignment when large journal batches are processed concurrently, with the workaround of serial submission and pauses ([KA-24233](https://community.dynamics.com/article/KA-24233)); supplying `lineNumber` explicitly and never writing to one batch from two threads removes the race.

## 4. Recommended approach and implementation plan

The recommendation in one sentence: **load sub-ledger open items first (bank, customers, vendors), each line balanced against a dedicated `OB-CLEARING` G/L account, then load the G/L trial balance with control-account lines redirected to `OB-CLEARING`, and sign off when the clearing account is 0.00 and the Microsoft reconciliation reports tie to the legacy closing pack.** G/L and bank lines go through the standard `journals`/`journalLines` API; customer and vendor lines go through a new custom AL API page in the existing extension; every batch is posted with the standard `Microsoft.NAV.post`. Inventory and fixed assets are *not* in the scripts' first scope (see 4.9) but are sequenced here so Finance sees the whole picture.

### 4.1 Phase 0: prepare BC (Finance + developer), in QA-AGI first

1. **Fix the cutover date** (`OB_POSTING_DATE`, last day of the period before go-live) and the legacy closing pack it must tie to: aged AR and AP by document with remaining amounts, bank book balances, trial balance, inventory valuation, FA register. ### 4.3 Phase 2: scaffold the scripts repository

Recommended shape: a .NET 10 console tool (working name `bcob`) in `src/BcOpeningBalances/`, tests in `tests/`, data in `data/` (git-ignored except templates), runbooks in `docs/`. .NET keeps the backend's typed-client idioms available for copy-paste while avoiding the host-bound pieces (Microsoft.Identity.Web, Postgres). Token acquisition uses MSAL `ConfidentialClientApplicationBuilder.Create(clientId).WithClientSecret(secret).WithAuthority(AzureCloudInstance.AzurePublic, tenantId)` → `AcquireTokenForClient(["https://api.businesscentral.dynamics.com/.default"])`, cached in memory and refreshed pre-emptively, exactly as BCTech's sample does ([BCTech CommonData.psm1](https://raw.githubusercontent.com/microsoft/BCTech/ccb6c3d36f72b784fb9757316f6f296f0a58ea71/samples/PSOAuthBCAccess/CommonData.psm1)). The HTTP layer copies five backend rules verbatim: `Accept-Language: en-US`; explicit `$select`/`$top` on every read; `Data-Access-Intent: ReadOnly` on reads only; **no automatic retry of any POST**; 429/503 handled by exponential back-off with jitter on *reads* and by "probe, then decide" on writes. Concurrency is **1** (one batch at a time, serial line inserts), which also respects KA-24233 and leaves the backend's four governor slots untouched.

Commands: `bcob validate <ledger>` (schema, master-data existence, sums, uniqueness of document numbers, posting-date window), `bcob plan <ledger>` (chunks into journal batches and writes the plan with every derived Document No.), `bcob load <ledger> --batch OB-AR-01` (probe → insert lines → post, one chunk), `bcob probe <batch>` (ledger evidence for an undecided chunk), `bcob reconcile` (pulls BC figures and writes the pack), `bcob report`. Every command is dry-run by default and needs `--execute` plus the environment name typed back (`--confirm QA-AGI`) to write. Tests follow the backend's gates: pure unit tests with a fake `HttpMessageHandler` and golden JSON payloads (contract tests pin the exact body shapes for `journalLines`, `openingJournalLines` and `$batch`), idempotency tests that count side effects, and `[BcFact]`-style live tests that skip unless `BC_INTEGRATION_TESTS=1` and that only ever target QA-AGI. A `workflow_dispatch` GitHub Actions workflow runs `validate`/`plan` on uploaded CSVs and `load` only with environment `qa` approval; a `.github/CODEOWNERS` and required reviewer on that environment make the "controlled-live gate" a GitHub control rather than a convention.

### 4.5 Phase 4: rehearse twice on QA-AGI

QA-AGI is a sandbox, so the first two full runs are the rehearsal; when a production environment exists, copy it to a sandbox and rehearse again on the copy because a copy carries the same version, PTEs and AppSource apps and there is no "refresh" (delete and re-copy between runs) ([Copy a Production or Sandbox Environment](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/tenant-admin-center-environments-copy)). Each rehearsal runs the full Phase 5 sequence with the real extracts, produces the Phase 6 pack, and records timings per chunk size (start at 200 lines per journal batch; the only hard figures are 100 operations per `$batch` and the 8-minute operation timeout, Microsoft publishes no recommended lines-per-post). Rehearsal exit criteria: clearing = 0.00; aged AR/AP tie; one deliberately injected failure (a blocked customer in chunk 3) leaves the earlier chunks posted, chunk 3 unposted and empty, and a second `load` run skips chunks 1-2 by probe and completes chunk 3; `Post with Job Queue` confirmed off; the DynamicERP extension shown not to interfere with journal posting.

### 4.6 Phase 5: cutover sequence (per company, run serially)

1. Freeze legacy; export the closing pack; `bcob validate` all four CSVs; Finance signs the extracts.
2. Phase 0 BC settings applied and screenshot into the cutover log (Allow Posting window, Direct Posting flags, batch settings, Post with Job Queue, depreciation-book integration toggles if FA is in scope).
3. `bcob load bank` → `OB-BANK` posts bank account ledger entries balanced to clearing (Account Type Bank Account through the standard API, which resolves bank `accountId`).
4. `bcob load ar` → `OB-AR-01..nn` through `openingJournalLines`, posted per chunk with `Microsoft.NAV.post`.
5. `bcob load ap` → `OB-AP-01..nn`, same path.
6. VAT opening balances, inventory (item journal, Positive Adjmt., per item/location/lot; Inventory Adjmt. account routed to clearing) and fixed assets (FA journal with integration off) are posted by Finance in the UI or by configuration package in this slot; they are outside the scripts' first scope.
7. `bcob reconcile --stage subledgers`: clearing balance must equal the sum of the control-account lines still to come from the TB (the sign-flipped total of the redirected lines); stop if not.
8. `bcob load gl` → `OB-GL`, the zero-sum trial balance with control lines redirected to clearing.
9. `bcob reconcile --stage final`: clearing = 0.00; the Phase 6 pack.
10. Phase 7 lock-down; Finance signs; go-live.

The sub-ledgers-first order is deliberate: under Technique B the clearing balance after step 7 is a checksum of what the TB must still supply, which catches a missing AR chunk before the G/L is touched; Microsoft's RapidStart tip of "G/L balances first, then open customer entries, then open item ledger entries" is equally valid and simply moves the checksum to the end ([Tips and Tricks: RapidStart Services (mirror)](https://business-central.to-increase.com/md/en-US/admin-tips-and-tricks-rapidstart-services.md)).

### 4.7 Phase 6: reconciliation pack and sign-off

`bcob reconcile` writes `reconciliation-{env}-{date}.md` with, per line, legacy figure, BC figure, variance, owner and approver. BC figures come from: `generalLedgerEntries?$filter=accountNumber eq 'OB-CLEARING'` summed (must be 0.00); `generalLedgerEntries?$filter=startswith(documentNumber,'OB-')` grouped by account against the TB; the custom `customerLedgerEntries`/`vendorLedgerEntries` pages (count of open entries = count of extract rows, Σ `remainingAmount` per customer = legacy per-customer total, per-document `dueDate`/`documentDate`/`currencyCode` equal to the extract); `customerFinancialDetail.balance` per customer as a second opinion via `$expand`; the standard `agedAccountsReceivable`/`agedAccountsPayable` report entities as of the cutover date against the legacy aged totals. Finance additionally runs the Microsoft report set in the UI: **Reconcile Cust. and Vend. Accs** (no differences), **Customer/Vendor - Trial Balance** (sub-ledger = control account), **Aged Accounts Receivable/Payable** by due date, **Detail Trial Balance** against the legacy TB, and the first **Bank Acc. Reconciliation** with no direct-posting warning ([Prepare pre-closing reports](https://learn.microsoft.com/en-us/dynamics365/business-central/year-prepare-preclose-reports); [Prepare to close statements](https://learn.microsoft.com/en-us/dynamics365/business-central/year-prepare-close-statement); [Reconcile bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/bank-how-reconcile-bank-accounts-separately)). The G/L Register numbers of every posted batch (from page 70117) go into the cutover log because the register is the audit trail and the rollback handle ([Analyze G/L entries](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-to-analyze-gl-entries)).

### 4.8 Phase 7: lock-down and rollback

Lock-down: Allow Posting From/To moved to the go-live date onward on General Ledger Setup, the application account's User Setup row removed, `OB-*` batches deleted or blocked, `OB-CLEARING` set to `Direct Posting = No`, depreciation-book integration restored, the Entra application's permission set reduced to what the logistics backend needs, and the closing fiscal year *not* closed and Close Income Statement *not* run until Finance signs the opening P&L, since a closed year cannot be reopened ([Close accounting periods](https://learn.microsoft.com/en-us/dynamics365/business-central/year-close-account-periods); [Close income statement accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/year-close-income-statement)).

Rollback is a UI operation that the scripts prepare but do not execute. A journal-posted entry can be reversed with **Reverse Transaction** only if unapplied, only once, with the same document number and posting date, and not when an Additional Reporting Currency is in use; a whole register is reversed with **Copy G/L Register to Journal** with opposite signs, available because `Copy to Posted Jnl. Lines` was enabled before posting ([Reverse journal postings](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-reverse-journal-posting)). Entries applied after go-live must be unapplied first ([Reconcile customer payments manually](https://learn.microsoft.com/en-us/dynamics365/business-central/receivables-how-apply-sales-transactions-manually)). Inventory and FA have no Reverse Transaction; their rollback is a negative item journal and a reversing FA journal with integration off. Because each chunk is its own register, a bad chunk is reversed alone and re-loaded with a new chunk suffix (`OB-AR-03b`), never re-posted under the same keys.

### 4.9 Which BC API path for each sub-ledger, and why

| Sub-ledger | Path | Why this and not the alternatives |
|---|---|---|
| G/L trial balance | Standard `POST journals({OB-GL})/journalLines` (G/L lines, `balanceAccountType` omitted), dimensions via `dimensionSetLines` or deep insert, then `Microsoft.NAV.post` | Every needed field is exposed; `accountId`/`accountNumber` resolve for G/L; `Copy VAT Setup to Jnl. Lines = No` keeps VAT off. A custom page would add nothing. |
| Bank | Standard `journalLines` with `accountType = "Bank Account"` and batch-level `balancingAccountId = OB-CLEARING` | Bank accounts are resolved by the standard page; posting through the bank account (not its G/L account) is Microsoft's explicit rule. |
| Customers | Custom `openingJournalLines` (page 70114) into `OB-AR-nn`, then standard `Microsoft.NAV.post` | Standard page forces blank Document Type and cannot set Due Date/Document Date/Currency; `customerPayments` forces Document Type Payment and needs a posted Sales Invoice to apply to. |
| Vendors | Same custom page into `OB-AP-nn` | Same reasons; `External Document No.` carries the vendor invoice number. |
| Inventory | Out of scripts scope (UI item journal with Item Tracking on Lines, or configuration package) | No standard v2.0 item-journal entity; lot/serial lines need the item-tracking page; a custom AL item-journal API is a later increment. |
| Fixed assets | Out of scripts scope (FA journal in UI with integration off) | Microsoft's documented manual procedure; low volume. |
| Verification | Standard `generalLedgerEntries`, `customerFinancialDetail`, aged report entities; custom pages 70115/70116/70117 | v2.0 has no customer/vendor ledger entry resource or register resource. |

Configuration packages through the automation API (`configurationPackages` with `Microsoft.NAV.import`/`apply`) were evaluated and kept as the **manual fallback** if the AL publish slips: they accept every table-81 field, but they need `Automation.ReadWrite.All` plus the D365 AUTOMATION set, run asynchronously with errors surfacing as counts rather than per-line responses, still require a separate post, and block user sessions during import ([configurationPackage resource](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/resources/dynamics_configurationpackage); [Import business data from other finance systems](https://learn.microsoft.com/en-us/dynamics365/business-central/across-import-data-configuration-packages)). A custom AL bound action or unbound codeunit that takes a whole JSON batch and posts in one server transaction is the other alternative; it would avoid per-line HTTP calls, but it moves parsing and validation logic into AL where the repo's testing conventions are weakest, and the standard `post` action already gives the one-transaction guarantee per batch. Exposing page 39 as an OData web service is discouraged by Microsoft because UI-page semantics leak into the service ([Known OData limitations](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/odata-known-limitations)).

### 4.10 Idempotency keys, batching limits and the run ledger

Business Central provides no server-side idempotency for journal lines and does not enforce uniqueness of Document No. in G/L Entry, so identity must be client-side and deterministic. The **idempotency key is the derived `Document No.`** (`OB-AR-{legacy_doc_no}` etc., Code[20]), with the raw legacy number in `External Document No.` (Code[35]); the batch's No. Series and Posting No. Series stay blank so BC never renumbers. The run ledger (`runs/{env}/{company}/{ledger}.jsonl`, committed to the branch after each run, never containing secrets) records one row per chunk with the backend's vocabulary: `Planned` → `Attempted` (lines inserted) → `Landed` (post 204 **and** ledger evidence found) / `NotLanded` (deterministic refusal before any write, e.g. 400 on line insert in a snapshot batch) / `Undecided` (timeout, 408/504, connection reset) / `Abandoned` (operator decision). The chunk algorithm: (1) **probe**: `GET generalLedgerEntries?$filter=documentNumber eq '{first doc no of chunk}'&$top=1` and, for AR/AP, `customerLedgerEntries?$filter=documentNo eq ...`; if found, mark `Landed` and skip; (2) `GET journals({id})/journalLines?$top=1`: if unposted lines exist from an earlier attempt, delete them (they are unposted staging rows, and the ledger probe just proved nothing posted) or refuse if they belong to another run; (3) insert the chunk's lines and the post action in **one `$batch` with `Isolation: snapshot`, ≤99 line inserts plus the post as the last inner request**, each line carrying an explicit `lineNumber` (10000, 20000, …); because codeunit 13 commits only at the end of a successful post, a failing post rolls the inserted lines back with it, so a failed chunk leaves the batch empty (an inference from the AL; the rehearsal must confirm) ([Using OData transactional $batch requests](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/use-odata-batch)); (4) on 204 run the probe again before marking `Landed`; (5) on any ambiguous outcome mark `Undecided`, wait past BC's ten-minute request limit, probe, and only then decide. For chunks larger than 99 lines, insert lines in several snapshot batches and post with a separate call, accepting that a crash between them leaves unposted lines that step 2 cleans up. Rate handling: concurrency 1; honour `Retry-After` on 429 for reads; never auto-retry a write. Chunk size 200 is the starting point for rehearsal timing; the only hard caps are 100 operations per `$batch` and the 8-minute operation timeout ([Operational limits](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/operational-limits-online)).

## Conclusion

The thing that makes this plan safe is not the API but the arithmetic: with every sub-ledger line balanced to `OB-CLEARING` and the trial balance's control-account lines redirected to the same account, Business Central's own journal-balancing rule guarantees that the clearing account can only reach 0.00 when every chunk has landed exactly once, which turns reconciliation from a report Finance reads into an invariant the scripts can assert. The logistics backend taught the same lesson in a different domain, that a BC write is a request whose outcome is learned by reading the ledger, and the opening-balance scripts inherit its vocabulary (probe, apply, settle) without inheriting its host.

The one piece of new Business Central code, a 70114 API page over `Gen. Journal Line`, exists only because Microsoft's standard page deliberately hides the fields that make an opening receivable a receivable; everything else is standard surface. That keeps the extension change small enough to publish to QA-AGI in a day and small enough that, once AGI is live, the same page serves the backend's future IF-14/IF-15 journal postings (transporter cost, driver collections) without another migration-specific design.
